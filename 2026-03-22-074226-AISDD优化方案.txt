  AISDD 工作流改进综合分析

  一、当前工作流的核心问题

  当前模式：单一串行 Agent，人工审批是唯一的质量关卡
  epicspec → featurespec×N → gate → epicplan → featureplan×N → gate → epicdesign
   × phases → gate → featuretasks×N → gate → implement → verify → gate

  三大结构性缺陷：

  ┌──────────────┬──────────────────────────────────────┬────────────────────┐
  │     缺陷     │                 表现                 │        风险        │
  ├──────────────┼──────────────────────────────────────┼────────────────────┤
  │ 单视角生成   │ 同一 Agent 生成                      │ 系统性偏差不被发现 │
  │              │ spec/plan/design，自我校验盲区大     │                    │
  ├──────────────┼──────────────────────────────────────┼────────────────────┤
  │ 质量关卡后置 │ 缺陷在 gate                          │ 大量返工           │
  │              │ 时才被人发现，越晚发现代价越高       │                    │
  ├──────────────┼──────────────────────────────────────┼────────────────────┤
  │ 串行执行     │ N 个 Feature spec/plan 逐一生成      │ 时间线性增长       │
  └──────────────┴──────────────────────────────────────┴────────────────────┘

  ---
  二、改进机会映射

  2.1 高价值改进：对抗性验证（Adversarial Validation）

  这是��值得引入的改进。核心思路：同一产物让不同角色的 Agent 独立"挑战"一遍。

  适用位置：

  featurespec 完成后  ──→  [Spec Challenge Agent Team]
                                ├── 需求完整性挑战者（漏洞/边界/矛盾）
                                ├── NFR 可行性挑战者（指标是否现实）
                                └── 范围蔓延检测者（超出 EPIC 目标的需求）

  epicplan/featureplan 完成后 ──→  [Plan Challenge Agent Team]
                                ├── 架构风险评审者（反模式/SOLID 违规）
                                ├── 技术债务评估者（过度设计/取巧）
                                └── 可测试性评审者

  epicdesign 完成后 ──→  [Design Challenge Agent Team]
                                ├── 安全评审者（设计阶段安全漏洞）
                                ├── 性能建模者（NFR 是否可达）
                                └── Android 最佳实践评审者

  新建命令建议：/aisdd.challenge

  # 用法
  /aisdd.challenge spec        # 挑战 spec
  /aisdd.challenge plan        # 挑战 plan
  /aisdd.challenge design      # 挑战 design

  # 内部实现
  - 并行启动 2-3 个 subagent，每个赋予不同"挑战角色"的 system prompt
  - 各 subagent 独立输出结构化问题列表（severity: BLOCK/WARN/NOTE）
  - 主 agent 合并去重，输出 challenge-report.md
  - 人类评审 challenge-report 后决定是否触发 /aisdd.cr

  价值评估： 最高。在 plan-ready gate 前引入，可显著减少 epicdesign 阶段的返工。

  ---
  2.2 中高价值改进：并行 Feature 处理

  当前 featurespec / featureplan 是逐个 Feature 串行生成。

  改进方案： 批量模式（Batch Mode）

  # 当前
  /aisdd.featurespec FEAT-001  →  /aisdd.featurespec FEAT-002  →  ...

  # 改进后
  /aisdd.featurespec --batch  →  主 agent 读 epic.md 获取 Feature 列表
                               →  为每个 Feature 启动独立 subagent（并行）
                               →  各 subagent 生成对应 spec.md
                               →  主 agent 汇总，运行跨 Feature 一致性检查

  注意事项：
  - 并行 subagent 需在同一 EPIC 分支，使用 isolation: "worktree" 避免写冲突
  - 完成后必须运行 /aisdd.epicanalyze（该命令已存在，职责匹配）
  - 适合 Feature ≥ 3 的大型 EPIC

  价值评估： 中高，时间节省与 Feature 数量成正比。

  ---
  2.3 中高价值改进：实现阶段并行化

  当前 implement 是完全串行的。tasks.md 中已有 [P]
  标记并行任务，但未被充分利用。

  改进方案： Story 级并行 Agent Team

  主 Agent（协调者）
  ├── 读取 tasks.md，识别无依赖的 Story 组
  ├── 为每组 Story 启动 subagent（isolation: "worktree"）
  │    ├── Story Agent A → 实现 ST-001（worktree-A 分支）
  │    ├── Story Agent B → 实现 ST-002（worktree-B 分支）
  │    └── Story Agent C → 实现 ST-003（worktree-C 分支）
  └── 各 subagent 完成后 → 主 Agent 合并 + 冲突解决 + 运行 /aisdd.verify

  实现复杂度较高，适合后期引入。关键约束：
  - 每个 subagent 只读其对应 story_detail_design.md 中的 L2 章节
  - 主 agent 持有集成权限，subagent 无权修改 spec/plan/design

  ---
  2.4 中价值改进：渐进式验证（Progressive Verify）

  当前 verify 在整个 EPIC 实现完成后才运行，发现问题时返工代价大。

  改进方案： 分级 Verify

  /aisdd.verify story ST-001    # Story 级：实现完一个 Story 立即验证
  /aisdd.verify feature FEAT-001  # Feature 级：一个 Feature 全部 Story
  完成后验证
  /aisdd.verify                  # EPIC 级（当前行为）：全部完成后验证

  修改 aisdd.implement.md，在每个 Story 完成后自动触发 /aisdd.verify 
  story，阻塞下游依赖 Story 的执行。

  价值评估： 中等，对于大型 EPIC（≥ 10 Story）价值显著。

  ---
  2.5 中价值改进：前置研究阶段

  新建命令：/aisdd.research（在 epicplan 之前，可选）

  主 Agent 触发两类 subagent 并行：
  ├── Codebase Discovery Agent：深度扫描现有代码，输出可复用组件清单
  └── Implementation Pattern Agent：搜索该 Feature 类型的 Android 最佳实践
  合并输出 research.md，注入到 epicplan 的 context 中

  这解决了 epicplan 生成时「不了解现有代码资产」的盲区。现有的 constitution.md
  要求演进式设计，但没有强制执行代码发现环节。

  五、关于 /aisdd.challenge 的具体设计

  这是 P0 建议，给你一个具体实现方向：

  # .claude/commands/aisdd.challenge.md

  ## 触发时机
  - /aisdd.challenge spec   → 在 gate spec-ready 之前运行
  - /aisdd.challenge plan   �� 在 gate plan-ready 之前运行
  - /aisdd.challenge design → 在 gate design-ready 之前运行

  ## 执行流程
  1. 读取目标文档（spec.md / plan.md / epic-design.md）
  2. 以 3 个不同角色的系统提示，启动 3 个 subagent（并行）：
     - Role A: "Requirements Completeness Auditor" - 找遗漏、边界、矛盾
     - Role B: "Technical Feasibility Skeptic" - 挑战 NFR、技术选型风险
     - Role C: "Scope & Complexity Watchdog" - 识别范围蔓延、隐性依赖
  3. 主 agent 合并三份报告，按 BLOCK/WARN/NOTE 分级
  4. 输出 challenge-report.md（不修改原文档）
  5. 人类决策：BLOCK 级别必须修复 → /aisdd.cr；WARN/NOTE 可酌情处理

  ## 输出格式
  | ID | 来源 Agent | 级别 | 位置（文档章节） | 问题描述 | 建议 |
  |----|-----------|------|----------------|---------|------|

  ---
  核心结论： 你的工作流框架已经相当成熟，最大的改进机会在于在每个关键阶段引入对
  抗性验证，而不是完全重构流程。把 gate 的质量压力分散到每个阶段的 challenge
  步骤，人在 gate 时看到的是「已经经过 AI
  挑战后的方案」，而不是「第一次生成的原始方案」。这才是 Agent Team
  技术在设计工作流中的核心价值。
