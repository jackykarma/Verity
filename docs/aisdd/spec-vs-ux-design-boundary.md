# spec.md 与 ux-design.md 的边界说明

> **定位**：说明 AISDD 工作流中 **Feature 产品规格**（`spec.md`）与 **EPIC 级体验呈现规格**（`ux-design.md`）的职责划分、重叠地带与实操判断方法，便于产品、设计与研发对齐事实源，减少重复与口径漂移。
>
> **相关文档**：`.specify/memory/constitution.md`（文档事实源）、`.specify/templates/spec-template.md`、`.specify/templates/ux-design-template.md`、`docs/workflow-overview.md`

---

## 一、章程中的事实源归属

`.specify/memory/constitution.md` 约定：

| 文档 | 事实源角色 | 主要内容 |
|------|------------|----------|
| `spec.md` | **需求事实源** | 范围（In/Out）、FR/NFR、验收标准、边界与异常场景 |
| `ux-design.md` | **体验呈现事实源** | 信息架构、交互规则与状态、视觉规范、动效清单与说明、设计稿索引 |

一句话：**`spec.md` 描述「系统必须做什么」（行为契约）；`ux-design.md` 描述「用户如何感知与操作」（呈现契约）。**

---

## 二、三个维度的划分

产品常从三个角度描述需求，可按下表区分归属：

| 维度 | 核心问题 | 归属文档 | 表述风格示例 |
|------|----------|----------|----------------|
| **产品 / 业务** | 在该场景下系统**必须产生什么结果**？ | `spec.md` | 「系统必须……」「用户必须能够……」 |
| **交互** | 用户通过**什么操作**触发？系统以**什么交互形态**反馈？ | `ux-design.md` | 「点击 → 打开 BottomSheet」「下拉 → 刷新」「加载中 → 骨架屏」 |
| **视觉** | **具体长什么样**？色值、间距、字号、动效参数？ | `ux-design.md` | 「Primary #1976D2」「圆角 12dp」「入场 300ms、EaseInOut」 |

**判断原则**：若把交互形式与视觉样式全部删掉后，剩下的「行为结果」仍然完整、可验收，则该部分属于 `spec.md`；若删掉后没有有效信息，则属于 `ux-design.md`。

---

## 三、重叠地带：异常与状态

同一类问题（如网络失败、空列表、权限拒绝）往往在两边都会出现，但**回答的侧面不同**。

### 示例：网络请求失败

| 层面 | 文档位置（模板章节） | 写什么 |
|------|----------------------|--------|
| 行为与验收 | `spec.md`「边界与异常场景」 | 网络失败时系统须提示错误、提供重试；已加载数据不丢失等 |
| 功能需求 | `spec.md`「FR」 | 如：离线须可查看已缓存内容 |
| 非功能 | `spec.md`「NFR」 | 如：超时阈值、降级策略、可观测性 |
| 状态长什么样 | `ux-design.md`「状态定义」 | 错误态：插画 + 文案 + 重试按钮；离线态：Banner + 缓存内容等 |
| 反馈形态 | `ux-design.md`「反馈方式」 | Snackbar / Dialog / 内联错误、时机与持续时间 |
| 异常交互流 | `ux-design.md`「异常与边界交互」 | 超时 → 展示错误态 + 重试 → 点击后重新请求 |
| 组件与视觉 | `ux-design.md`「组件清单」「视觉规范」 | 卡片样式、按钮类型、色板与间距 |

归纳：

- **`spec.md`**：失败时**必须怎样**（可测试、与设计稿无关）。
- **`ux-design.md`**：**看起来怎样、怎么点**（须设计稿或明确标注的兜底建议）。

## 四、实操判断清单

不确定一条内容写在哪份文档时，可依次自问：

| 问题 | 若结论为 | 写入 |
|------|----------|------|
| 去掉这条后，功能逻辑仍完整吗？ | 不完整 | `spec.md`（行为契约） |
| 是否在描述控件、手势、动画、布局？ | 是 | `ux-design.md` |
| 能否改写成「系统必须……」且仍成立？ | 能 | `spec.md` FR |
| 是否依赖设计师出图才能定稿？ | 是 | `ux-design.md` |
| 是否含可量化指标（时间、比例、阈值）？ | 是 | `spec.md` NFR（及 plan 中的测量方式） |
| 是否在描述「某状态下界面呈现」？ | 是 | `ux-design.md` |
| 是否在描述「何时进入/退出某状态」（业务语义）？ | 是 | `spec.md`（旅程、边界、FR） |

## 五、模板设计意图（为何这样拆）

- **`spec-template.md`** 中与呈现相关的表述刻意保持抽象：边界场景写「期望行为 / 提示 / 降级」，不写具体控件；用户旅程写「预期结果」而非像素级界面。
- **`ux-design-template.md`** 要求交互与视觉条目**标注设计稿来源**，并通过「遗漏与待确认」与各 Feature `spec.md` 交叉比对，暴露「需求有、稿子里没有」的缺口。

含义：**`spec.md` 可在无设计稿时定稿；`ux-design.md` 以设计稿为权威输入**（无稿时的 AI 建议须标 `[AI 建议 - 待设计师确认]`，见 `/aisdd.epicuidesign` 行为约束）。

---

## 六、对技术方案与工作量的传导

三者都会影响实现与排期，在工作流中通过下游文档合流，而不是在 spec 与 ux 中重复写技术方案：

```text
spec.md（做什么）     ─┐
                        ├──→ 各 Feature plan.md、epic-design.md ──→ tasks.md → 实现
ux-design.md（怎么呈现）─┘
```

- **`plan.md` / `epic-plan.md`**：同时消费需求与 UX 约束，落到接口、数据、线程、错误模型与工作量。
- **`epic-design.md`**：输入中明确包含 `ux-design.md`（若已产出），用于架构与界面层设计一致。

好处：**产品与体验规格阶段边界清晰**；**plan / design 阶段统一消化技术与工作量**；**遗漏清单**驱动补设计或补需求。

## 七、速记公式

| 文档 | 概括 |
|------|------|
| **`spec.md`** | **What + When + 量化指标**——在什么条件下，系统必须达成什么可验收结果。 |
| **`ux-design.md`** | **How it looks + How to interact**——用户看到什么、如何操作、动效与适配如何规定。 |

对「异常 / 状态」：**`spec.md` 管必须处理到什么程度；`ux-design.md` 管用什么形态让用户感知并完成操作。**

## 八、工作流中的边界守护机制

为防止边界混淆，工作流在两个写入阶段内建了**自动边界检查**：

### 8.1 featurespec 阶段（写 spec.md 时）

规则位于 `.cursor/commands/aisdd.featurespec.md`「spec / ux-design 边界守护」章节。

当 AI 检测到即将写入 spec.md 的内容含有交互形态（控件/手势/动画）、视觉细节（色值/间距/动效参数）、布局结构或状态视觉表现时：

1. **不直接写入**
2. 向用户列出疑似越界条目并标注建议归属
3. 等待用户选择：移入 ux-design 待写清单 / 确认保留 / 拆分处理

### 8.2 epicuidesign 阶段（写 ux-design.md 时）

规则位于 `.cursor/rules/aisdd-epicuidesign.mdc`「spec / ux-design 边界守护」章节。

当 AI 检测到即将写入 ux-design.md 的内容含有行为契约（「系统必须……」）、量化指标、范围定义或状态进入/退出的业务规则时：

1. **不直接写入**
2. 向用户列出疑似越界条目并标注建议归属
3. 等待用户选择：移入 spec.md 补充清单 / 确认保留 / 拆分处理

### 8.3 结构化输入增强 AI 理解

规则位于 `.cursor/rules/aisdd-epicuidesign.mdc`「设计素材」和「输入质量分级与置信度」章节。

纯图片识别存在精度瓶颈（间距 ±4dp、色值偏差、动效不可见），因此工作流引入两种结构化补充输入：

- **`design/design-notes.md`**（模板：`.specify/templates/design-notes-template.md`）：设计师/产品手写的结构化上下文，覆盖图片间关系、精确色值与间距、交互细节、动效参数、导航结构等 AI 无法从截图推断的信息
- **`design/design-tokens.json`**（模板：`.specify/templates/design-tokens-template.json`）：从 Figma/设计工具导出的精确色值、间距、字号、圆角、高程等设计变量

**输入优先级**：design-notes 文字 > design-tokens 数值 > Pencil 节点树 > 图片视觉识别。当不同来源冲突时采信高优先级，并在 ux-design.md「输入源冲突」章节记录。

AI 对每条提取结果标注置信度（`✅ 高` / `⚠️ 中` / `❓ 低`），帮助 reviewer 快速聚焦需要人工确认的条目。

### 8.4 AI 视觉理解验证图

规则位于 `.cursor/rules/aisdd-epicuidesign.mdc`「AI 视觉理解验证图」章节，模板位于 `.specify/templates/ux-design-template.md`「AI 视觉理解验证图」章节。

AI 在解析视觉稿后，必须用绘图方式展现其对 UI 结构、布局和视觉规范的理解：

- **关键界面布局结构图**：线框级草图，标注区域划分、组件类型与位置
- **状态切换示意图**：多状态界面的各状态视觉对比
- **页面流转缩略图**（可选）：核心旅程的多屏缩略流程

图片存放于 EPIC 的 `design/ai-understanding/` 目录，在 `ux-design.md` 中引用并附理解要点文字。开发者通过比对 AI 生成的理解图与原始设计稿，快速发现 AI 理解偏差，在进入下游设计/实现阶段前纠正。
