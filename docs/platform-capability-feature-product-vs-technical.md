# Platform-Capability 类型 Feature：产品层面能力需求 vs 交付/拆分层面表述

本文档说明 Speckit 中 **Platform-Capability** 类型 Feature 的定位：其**类型标签**属于**交付结构/拆分层面**的表述（而非实现阶段的技术方案），**该 Feature 内部的需求**可同时包含产品层面的能力诉求与后续在 plan 阶段细化的技术表述。便于产品、SE、开发在写 epic/spec 时统一口径。

---

## 1. 结论摘要


| 维度                            | 结论                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| **「Platform-Capability」这个类型** | **交付结构/拆分层面**的表述：描述该 Feature 在**交付物与依赖关系**中的角色（共享能力、可独立交付与验收），而非用户直接诉求；**不依赖** Specify 阶段已有技术方案。 |
| **该类型 Feature 内部的需求**         | **可兼有**产品层面能力需求（体验、性能、合规等）与在 plan 阶段细化的技术表述（接口、实现、交付形态）；spec 阶段侧重可验收的结果与边界。                      |
| **与「产品层面的能力需求」的关系**           | 产品关心的是**结果**（能读图、加载快、权限体验好）；是否用「Platform-Capability」来承载这些结果，是**交付拆分与依赖结构**的决策，不是产品术语。            |

## 2. 「Platform-Capability」类型：交付结构/拆分层面的表述

### 2.1 类型在回答什么

- **Product Feature**：直接对应用户/业务价值（如「时间轴浏览」「大图浏览」），PRD/产品会直接描述这类需求。
- **Platform-Capability Feature**：用户不会说「我要媒体库访问能力」，只会说「我要看照片」。把「媒体库访问」「图片加载框架」拆成**独立 Feature**，是**交付与依赖结构的决策**——为了复用、一致性、可验收，把「能力」单独做成一个交付单元。

因此：**「Platform-Capability」这个类型是交付结构/拆分层面的表述**，用来区分「直接面向用户的 Product」与「为多个 Product 提供能力的共享能力单元」。它描述的是**交付物的形状与依赖关系**，不要求此时已有具体技术方案。

### 2.2 在模板中的依据

- epic 模板中：当某能力需要**可独立交付 + 可版本化 + 可复用 + 可验收**时，应**升级为 Capability Feature** 并登记。
- 通用能力一节描述的是**跨 Feature 的平台能力/设计决策/通用组件**——既有「能力」（产品/业务会关心的结果），也有「交付形态与依赖」的决策。

类型本身描述的是**该 Feature 在整体交付结构中的角色**，属于「拆分与依赖」范畴，不是纯产品语言；也**不要求**在 Specify 阶段已存在具体技术方案。

### 2.3 常见疑问：Specify 阶段还没有技术方案，为何就有「架构」考虑？

**疑问**：既然是技术/架构层面的表述，而 Specify 阶段还没有真正考虑过技术方案，那么怎么会有技术架构方面的考虑？

**澄清**：

- **Specify 阶段不做「技术方案设计」**：不选型 Glide/Coil、不设计 Repository 接口、不画类图。技术方案在 **Plan 阶段**（epic-arch + feature plan）才展开。
- **Specify 阶段会做「交付与依赖的拆分」**：要回答的是「哪些东西作为**独立交付单元**、谁依赖谁」。例如：「时间轴、大图、图集都要读照片 → 把『能读照片』做成一个独立交付单元，大家复用」——这是**交付物形状与依赖关系**的决策，**不需要**先有 MediaStore 封装方案才能做。
- 因此更精确的说法是：**「Platform-Capability」是「交付结构/拆分层面」的表述**，描述的是「这是一个共享能力、一个独立交付单元」，而不是「我们已经定了技术实现」。  
「架构」在这里指的是**交付物与依赖的结构**（what are the units of delivery, who depends on whom），不是**实现架构**（how to implement）。前者在 Specify 阶段根据需求与复用关系就能判断；后者留给 Plan 阶段。

总结：在 Specify 阶段识别出 Platform-Capability，**不需要**事先有技术方案，只需要识别出「多个 Product 依赖同一类能力 → 把该能力拆成单独的可交付单元」即可。

### 2.4 常见疑问：Platform-Capability 涉及业务层的东西吗？

**疑问**：Platform-Capability 是交付结构/平台能力的表述，那它涉及业务层的东西吗？

**澄清**：

- **从类型定义本身**：Platform-Capability 只说明「这是一个共享能力、可独立交付单元」，**不**表示「这里必须没有业务」或「必须有业务」。类型描述的是交付结构中的角色，不直接回答是否涉及业务层。
- **从实际内容看**：
  - **会涉及业务侧诉求**：Capability 的 NFR/验收里常包含业务/产品关心的**结果与约束**——例如权限引导体验、合规（最小权限、隐私政策）、加载速度指标（首帧 < 300ms/500ms）、范围约束（仅读不写、不上传）。这些是「业务层」关心的**结果与边界**，应写在 spec 里。
  - **通常不承载业务规则/领域逻辑**：**领域规则与用例逻辑**（如「按日期分组」「快滑条对应哪段时间」「图集列表的排序规则」）一般放在**使用该能力的 Product Feature** 里；Capability 提供的是**能力**（能读图、能快速加载），不负责「相册这个业务该怎么用这些能力」。

**小结**：Platform-Capability **会涉及**业务层的「结果与约束」（体验、合规、性能指标等），但**一般不承载**业务层的「规则与领域逻辑」；业务规则由消费该能力的 Product Feature 负责。

## 3. 能力需求本身：可同时包含产品侧与技术侧

虽然**类型**是交付结构层面的表述，**该 Feature 内部的需求**不必也不应写成「纯技术」：

### 3.1 产品层面的能力需求（应写入 spec）

- **体验与合规**：权限流程用户体验良好、符合最小权限与隐私政策。
- **可验收的指标**：列表缩略图首帧 < 300ms、大图首帧 < 500ms、权限引导清晰可完成等。
- **业务约束**：如「仅读取、不写入」「不支持云端」等范围边界。

这些是**产品/业务/体验角度的能力诉求**，应作为 FR/NFR、验收意图写在 Feature 的 spec 中，便于产品与测试验收。

### 3.2 技术层面的表述（实现与接口，多在 Plan 阶段细化）

- **实现方式**：封装 MediaStore API、集成 Glide/Coil、缓存策略、权限申请流程的技术实现。
- **接口与契约**：如 `MediaRepository.getPhotos()`、`ImageLoader.load(uri, config)`、SDK 形态等。
- **交付物形态**：SDK/Repository 层/配置/资源包等。

这些是**技术设计与实现**，在 Specify/spec 阶段可仅写「需要统一接口/可复用」等约束；具体接口与实现细节在 **plan/tasks** 阶段展开。

### 3.3 二者在同一 Feature 中的关系

- **产品层面能力需求**：回答「要达成什么结果、如何验收」（体验、性能、合规）。
- **技术层面表述**：回答「通过什么接口与实现来达成」。

同一 Platform-Capability Feature 的 spec 中，应**同时写出**可验收的产品级结果（NFR/AC）与对接口/形态的约束，避免只写技术实现、无法做产品侧验收。

## 4. 与模板用词的对齐

- **通用能力**：记录的是「跨 Feature 的平台能力/设计决策/通用组件」——能力清单中的「关键约束（含隐私/性能预算）」即产品侧诉求；「交付物形态」「关键接口/契约」即技术侧表述。
- **Feature 列表的「业务/技术价值」列**：Capability 行常为「统一封装…供其他 Feature 复用」「统一…保证性能和稳定性」——前半是技术手段，后半（性能、稳定性）是产品/体验关注点。

书写时保持：**价值与验收偏产品/体验，拆分与形态偏交付结构**（具体技术形态在 Plan 阶段再定）。

---

## 5. 实践建议

1. **写 epic.md 时**：为 Platform-Capability 类型 Feature 填写「业务/技术价值」与「验收意图」时，**显式写出产品可验收的结果**（如加载时间、权限流程、合规要求），而不仅是「提供某某接口」。
2. **写 spec.md 时**：该类型 Feature 的 FR/NFR 应包含**可测试的体验与性能指标**；接口与实现约束可作为「技术约束」或「对外契约」单独小节，不替代产品级验收标准。
3. **沟通时**：向产品说明「Platform-Capability」是**交付结构上的分类**（共享能力、独立交付单元），不依赖「先有技术方案」；且该类 Feature 仍然有产品可验收的能力与指标，产品与测试可参与验收。
