# 背景与核心概念

> **一句话理解**：Choreographer 是 App 帧调度的指挥官——它不只是接收 Vsync，更是把 Input、Animation、Layout/Draw 这些工作统一编排在 Vsync 节拍上，保证每一帧的工作有序且及时完成。

---

## 1. 没有 Choreographer 之前（Android 4.0 及以前）

Android 4.0 之前，绘制是"随时触发"的：

- 调用 `invalidate()` → 立刻往消息队列发一条 `MSG_INVALIDATE`
- 主线程处理到这条消息时才 draw
- 和 Vsync 没有任何同步关系

**问题**：App 的绘制时机完全随机，可能刚好在两次屏幕刷新之间，导致：

```
屏幕刷新周期：  |──16ms──|──16ms──|──16ms──|
App 绘制时机：    ↑提交帧       ↑提交帧
                  （不在 Vsync 边界，显示器读到半完成的帧）
```

结果就是画面撕裂（tearing）和不规律的卡顿——即使 CPU 算力够用，帧也会乱。

---

## 2. Project Butter（Android 4.1 Jelly Bean）

Google 在 Android 4.1 提出 **Project Butter**，核心目标：让每一帧的绘制工作都严格对齐 Vsync 节拍，达到稳定 60fps。

三个关键改动：

| 改动 | 内容 | 解决的问题 |
|------|------|----------|
| **Vsync 扩展** | 将硬件 Vsync 信号同步分发给 App 和 SurfaceFlinger | App 绘制时机乱 |
| **Triple Buffering** | 三缓冲减少 App 等待空闲 Buffer 的概率 | Buffer 不够用导致的掉帧 |
| **Choreographer** | 统一调度 App 内所有需要帧同步的工作 | 各模块绘制互相干扰 |

Choreographer 就是 Project Butter 里负责"让 App 所有工作都跟着 Vsync 走"的核心组件。

---

## 3. Choreographer 的完整职责

很多人只知道 Choreographer 接收 Vsync，但它的完整职责有三层：

### 职责 1：Vsync 请求与接收

Choreographer 不会持续接收 Vsync（那样太耗电）。它的策略是**按需请求**：

- 只有当有回调待执行时，才向系统请求下一个 Vsync
- Vsync 到来后执行回调，然后停止请求
- 下次有新回调加入时，再次请求

这就是为什么 App 空闲时不消耗 Vsync 资源，只有有动画或触摸时才"活跃"。

### 职责 2：统一编排 4 类帧工作

Choreographer 把一帧内需要做的事分成 5 类（按执行顺序）：

```
CALLBACK_INPUT          (0) ← 输入事件处理（触摸、按键）
CALLBACK_ANIMATION      (1) ← 属性动画、ValueAnimator 等
CALLBACK_INSETS_ANIMATION (2) ← 系统栏插入动画（Android 11+）
CALLBACK_TRAVERSAL      (3) ← View 树遍历（measure/layout/draw）
CALLBACK_COMMIT         (4) ← 帧提交后处理（FrameMetrics 等）
```

这个顺序不是随意的——**必须先处理 Input，才能正确触发动画；必须动画算完，才能 layout/draw 最新状态**。

### 职责 3：维护帧时间戳

Choreographer 向所有回调传递 `frameTimeNanos`——本帧的 Vsync 时间戳（纳秒）。

这个时间戳的作用：
- 所有动画用它计算当前进度（保证同一帧内所有动画时间一致）
- FrameMetrics 用它计算帧耗时
- 帧率监控工具用它计算两帧之间的时间差

---

## 4. Choreographer 是每个线程一个

这是很多人不清楚的点：**`Choreographer.getInstance()` 返回的是当前线程的 Choreographer 实例**。

```kotlin
// 内部实现
fun getInstance(): Choreographer {
    return sThreadInstance.get()  // ThreadLocal，每个线程独立的实例
}
```

一个线程要使用 Choreographer，必须有 `Looper`。

**实践中**：通常只有主线程的 Choreographer 有意义（因为 View 系统在主线程），RenderThread 有自己的机制不依赖 Choreographer 对外 API。

---

## 5. Choreographer 和 Vsync 的关系

一句话：**Choreographer 是 Vsync 在应用层的消费者，不是 Vsync 的产生者**。

```
产生者：屏幕硬件（60/90/120Hz）
传递者：SurfaceFlinger（EventThread → DisplayEventReceiver）
消费者：Choreographer（收到 Vsync → doFrame() → 触发应用工作）
```

Vsync 从硬件到 Choreographer 的完整路径，是下一章的重点。

---

## 6. 常见误区

| 误区 | 真相 |
|------|------|
| "Choreographer 就是接收 Vsync 的" | 它是接收 + 编排。核心价值在于编排 5 类回调的顺序 |
| "调用 invalidate() 会立刻触发 onDraw()" | invalidate() 只是向 Choreographer 注册一个 TRAVERSAL 回调，等下一个 Vsync 才执行 |
| "一个 App 只有一个 Choreographer" | 每个有 Looper 的线程都可以有自己的 Choreographer |
| "App 一直在接收 Vsync" | 只有注册了回调时才请求 Vsync，空闲时不接收 |
| "Vsync 直接从硬件发到 App" | 经过 SurfaceFlinger → EventThread → DisplayEventReceiver → Choreographer |

---

## 7. 小结

- Choreographer 在 Android 4.1 引入，是 Project Butter 的核心组件
- 三大职责：按需请求 Vsync、按顺序编排 5 类帧回调、维护帧时间戳
- 每个有 Looper 的线程一个实例（ThreadLocal）
- 它是 Vsync 的消费者，不是产生者；Vsync 从硬件经多个中间层才到达 Choreographer
