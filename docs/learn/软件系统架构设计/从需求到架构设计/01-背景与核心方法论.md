# 从需求到架构设计｜背景与核心方法论

## 1. 问题起源

很多团队在做设计时会出现两个极端：

- 极端一：没有设计，直接开始写代码
- 极端二：设计文档很多，但和真实问题脱节

这背后的根因往往不是“不懂图”，而是没有建立一条稳定的设计递进方法。  
所以，本主题最重要的不是背概念，而是学会一条可重复的思考顺序。

## 2. 为什么架构设计不能从图开始

图是表达工具，不是设计起点。

如果从图开始，很容易出现：

- 直接套模板
- 图和真实业务问题脱节
- 模块边界来自经验偏好，而不是需求约束
- 类图看起来完整，但协作关系不支撑主流程

更合理的顺序是：

```text
需求 -> 问题 -> 边界 -> 协作 -> 分层 -> 模块 -> 详细设计 -> 图表表达
```

## 3. 核心方法论

### 3.1 从问题出发，而不是从方案出发

设计前先明确：

- 真正的问题是什么
- 问题出现在哪个场景
- 什么算解决了问题
- 不解决什么

如果一开始就进入“用什么模式、怎么分层”，通常会过早收敛。

### 3.2 从边界出发，而不是从实现出发

边界决定后续一切：

- 系统负责什么
- 模块负责什么
- 对外接口应该暴露什么
- 哪些复杂性应该被隔离

如果边界不清，后续类图、流程图、时序图都会互相穿透。

### 3.3 从协作出发，而不是从对象列表出发

系统设计最终要支撑“事情如何发生”。

所以要优先思考：

- 谁发起
- 谁编排
- 谁处理规则
- 谁负责存储
- 谁依赖外部系统

这比先列一堆类名更有价值。

### 3.4 从重点出发，而不是平均用力

不是所有部分都值得做同样细的设计。

应优先深入：

- 高风险模块
- 高复杂模块
- 高价值模块
- 高频变化模块

这就是为什么“关键模块设计”是必经步骤。

## 4. 一条稳定的设计递进链路

### 步骤 1：需求输入与问题澄清

你要把需求转成设计输入，而不是照抄需求描述。

建议固定回答：

- 目标是什么
- 用户是谁
- 核心场景是什么
- 输入输出是什么
- 约束是什么
- 成功标准是什么
- 非目标是什么

### 步骤 2：业务边界与系统边界识别

这一层的关键是判断：

- 系统边界在哪里
- 外部依赖有哪些
- 本次设计覆盖哪些能力
- 哪些是外部能力，不应强行设计进系统

### 步骤 3：`0` 层架构设计

关注系统在整体环境中的位置：

- 用户
- 外部系统
- 核心输入输出
- 上下游关系

### 步骤 4：`1` 层架构设计

关注系统内部如何分工：

- 分层
- 分模块
- 职责划分
- 数据流与调用流

### 步骤 5：关键模块设计

识别真正需要深入设计的部分，并明确：

- 模块职责
- 输入输出
- 状态
- 扩展点
- 风险点

### 步骤 6：`2` 层详细设计

继续推导：

- 类与接口
- 主流程与异常流程
- 数据结构
- 状态机
- 错误处理

### 步骤 7：图表表达与文档化

把思考结果用合适的图表达出来，而不是反过来用图驱动思考。

### 步骤 8：评审、收敛与迭代

回到最初的问题，验证：

- 是否真的解决问题
- 是否边界清晰
- 是否成本可接受
- 是否具备扩展空间

## 5. 设计输入模板

建议每次拿到需求都先写出这张表：

| 项目 | 内容 |
|------|------|
| 需求目标 | 本次要解决什么问题 |
| 用户与角色 | 谁会使用、谁会参与 |
| 核心场景 | 最重要的 1~3 个场景 |
| 输入 | 系统收到什么 |
| 输出 | 系统产出什么 |
| 约束 | 性能、稳定性、时间、成本、合规等 |
| 成功标准 | 怎样算设计成功 |
| 非目标 | 本次不解决什么 |

## 6. 一个简单的因果链记忆法

可以用一句话记住：

**先定义问题，再划边界；先看协作，再定结构；先抓重点，再落细节。**

## 7. 常见误区

- 一开始就讨论技术方案，而不是先澄清问题
- 只讲模块，不讲边界
- 只讲结构，不讲主流程
- 只讲正常流程，不讲异常路径
- 详细设计先于架构设计

## 8. 本章小结

本章最重要的收获是：

- 架构设计不是从图开始，而是从问题和边界开始
- 一条稳定的设计递进链路比记住零散概念更重要
- 后面的 `0` 层、`1` 层、`2` 层其实是在回答不同层次的问题
