# 从需求到架构设计｜常见陷阱与评审要点

## 1. 为什么需要专门看陷阱和评审

很多设计看起来“结构完整”，但真正进入实现阶段后会暴露问题。  
所以学习架构设计不能只看正向方法，还要学会识别坏味道，并通过评审收敛设计质量。

## 2. 常见陷阱

### 2.1 直接从需求跳到类图

表现：

- 需求刚明确一点，就开始列类名和接口
- 类图很丰富，但没有边界和主流程支撑

问题：

- 对象职责不稳定
- 后期改动大
- 类图只是静态想象，无法支撑真实业务

### 2.2 先套架构模板，再找需求

表现：

- 先决定一定要用某种架构模式
- 再强行把需求塞进去

问题：

- 设计失去针对性
- 结构复杂度高于需求本身
- 容易造成过度设计

### 2.3 把所有模块设计到同样细

表现：

- 每个模块都要画类图、时序图、流程图

问题：

- 成本高
- 信息噪声大
- 设计重点不突出

### 2.4 分层图画得好看，但职责不清

表现：

- 有表现层、应用层、领域层、基础设施层
- 但具体职责说不清楚

问题：

- 后续实现时容易层层穿透
- 所有逻辑最后堆在一个 Service 里

### 2.5 只设计正常流程，不设计异常路径

表现：

- 图上只有 happy path

问题：

- 真实系统一上线就暴露大量边界问题
- 评审时看起来没问题，实现时问题很多

### 2.6 把评审当成“看格式”

表现：

- 只看有没有图、章节齐不齐

问题：

- 评审没有触达设计本身
- 真正的边界、依赖、复杂度问题被忽略

## 3. 评审时应该重点看什么

### 3.1 问题是否被正确定义

先问：

- 设计解决的是不是真问题
- 目标和非目标是否清楚
- 设计输入是否完整

### 3.2 边界是否清楚

重点看：

- 系统边界清不清
- 模块边界清不清
- 对外接口边界清不清
- 外部依赖职责是否被错误纳入系统内部

### 3.3 分层和模块职责是否合理

重点看：

- 模块是否围绕职责划分
- 模块之间是否高内聚低耦合
- 是否存在“万能模块”或“巨型服务”
- 依赖方向是否稳定

### 3.4 主流程和异常流程是否都被覆盖

重点看：

- 正常路径是否完整
- 异常路径是否被识别
- 状态流转是否闭环
- 重试、降级、回滚等策略是否合理

### 3.5 是否存在过度设计

重点看：

- 复杂度是否明显高于当前需求
- 是否为了“将来可能用到”加入太多结构
- 是否引入了当前团队难以驾驭的模式

### 3.6 是否能落地

重点看：

- 研发是否能按这个设计实现
- 测试是否能按这个设计验证
- 上线后是否容易定位问题
- 运维和演进成本是否可接受

## 4. 一份实用评审清单

### 设计输入

- [ ] 目标清晰
- [ ] 场景清晰
- [ ] 约束清晰
- [ ] 非目标明确

### `0` 层架构

- [ ] 系统边界明确
- [ ] 外部依赖明确
- [ ] 上下游关系明确

### `1` 层架构

- [ ] 模块划分合理
- [ ] 模块职责清晰
- [ ] 依赖方向合理
- [ ] 数据流和调用流清楚

### 关键模块设计

- [ ] 复杂模块已识别
- [ ] 重点模块已下钻
- [ ] 扩展点与风险点被说明

### `2` 层详细设计

- [ ] 类和接口职责合理
- [ ] 时序图覆盖主流程
- [ ] 流程图覆盖判断分支
- [ ] 异常路径覆盖关键场景

### 落地性

- [ ] 实现成本可接受
- [ ] 测试可验证
- [ ] 未来演进可承受

## 5. 一个简单的评审思路

可以固定按这四个问题去看设计：

1. 这个设计解决了什么问题？
2. 为什么要这样划边界和职责？
3. 这套结构怎么支撑主流程和异常流程？
4. 这样设计的代价是什么？

如果这四个问题回答不清楚，设计通常还不够成熟。

## 6. 本章小结

本章最重要的结论是：

- 好设计不是“图多”，而是“问题清、边界清、协作清、代价清”
- 评审不是审格式，而是审设计逻辑
- 会识别陷阱，才能真正提升设计能力
