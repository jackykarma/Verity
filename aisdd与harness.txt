  ---
  二、核心差距

  差距 1：Gate 关卡无 harness 级执法

  现状：gate 检查完全依赖 AI 在 prompt 中提醒用户（"请先运行 /aisdd.gate 
  spec-ready"），无任何技术拦截。

  影响：用户可忽略提醒直接跳过 gate，AI 在显式参数（"强制/force"）下也会放行。

  缺口：没有配置任何 Hook（如 PreToolUse 或 Stop）来检查 gate-log.md
  状态并真正阻断流程。

  ---
  差距 2：PowerShell 脚本无全�� Bash 权限

  现状（settings.local.json）：仅有针对特定路径的 Bash(find ...) 等细粒度权限。

  问题：所有 AISDD 命令都依赖 pwsh -NoProfile -File 
  .\.specify\scripts\powershell\*.ps1，但没有 Bash(pwsh:*)
  权限，意味着每次执行都需要用户手动批准。

  ---
  差距 3：handoffs 只是 UI 提示，不是自动化

  现状：
  handoffs:
    - label: 一致性分析
      agent: aisdd.analyze
      send: true   # 会自动发送下一条 prompt

  send: true 确实会在命令完成后自动触发下一个
  skill，但这依赖命令正常完成后的单向传递，无法处理错误分支、条件路由（如 gate 
  未过时走不同路径）。

  ---
  差距 4：工作流状态无跨会话持久化

  现状：gate-log.md 作为文档级状态，每次新会话中 AI 需重新读取才知道当前阶段。

  缺口：没有利用 Claude Code 的 memory 系统在 memory/ 目录中持久化"当前
  EPIC、已过关卡、活跃 Feature"等状态，导致每次对话都要重新定向。

  ---
  差距 5：verify 的并行子 Agent 无权限保障

  aisdd.verify.md L3 EPIC 级验证明确要求"为每个 Feature 启动独立子 Agent"，但
  settings.local.json 中没有 Agent(*)
  或相关授权，实际能否自动并行取决于默认权限模式。

  ---
  三、哪些是设计选择，哪些是真正的缺口

  │ 无条件路由     │                    │                                    │

  └────────────────┴────────────────────┴────────────────────────────────────┘

  ---
  四、建议优先修复

  1. 权限白名单：在 settings.local.json 加入 Bash(pwsh:*) 或更精确的 Bash(pwsh 
  -NoProfile -File .specify/scripts/**)，避免每步都需手动批准。
  2. memory 状态文件：在 memory/ 目录维护 workflow-state.md，记录当前活跃 EPIC
  ID、已过 gate、活跃 Feature，供跨会话快速定向。
  3. 可选 Stop Hook：配置 Stop hook 在每次 AI 停止响应后输出"当前阶段 +
  建议下一步"，减少用户遗忘流程节点的情况。

  ---
  总结：AISDD 是文档驱动、人工触发的工作流，harness 被用作命令加载器和提示引擎，
  但自动化执法（hooks）、权限白名单、跨会话状态三块与 harness engineering
  的深度集成是主要差距。

  Harness Engineering 是什么（OpenAI 定义）

  OpenAI 的文章描述了他们用 Codex 构建产品时发现的一种新工程范式：当 AI 
  负责写代码，人类工程师的工作转变为：

  2. 规格化意图（Specify intent）——明确告诉 AI 要做什么、边界在哪
  3. 构建反馈环（Build feedback loops）——让 AI 可靠地完成工作的校验机制

  三名工程师驱动 Codex，无一行人工编写代码，平均每人每天 3.5 个 PR 合入。

  ---
  /aisdd.verify 根据层级输出不同粒度的报告：

  L1 Story 级 → 轻量验证卡，每个 Story 4 行结论：
  - 接口契约：✅/❌
  - 行为一致性：✅/❌
  - FR 覆盖：✅/⚠️/❌
  - 结论：通过 / 有偏离（偏离 ID）

  L2 Feature 级 → 完整报告，增加：
  - 架构一致性（包/模块结构是否符合设计）
  - 技术规约（线程模型、命名规范）
  - NFR 静态评估
  - FR/NFR 覆盖矩阵

  L3 EPIC 级（默认） → 以上全部 + 跨 Feature 汇总：
  - 各维度通过率表格
  - 偏离清单（按 BLOCK/WARN 分级）
  - 综合评级（✅ / ⚠️ / ❌）

  所有层级共同输出：
  - tasks.md 中被验证的 Task 追加验证标注
  - 建议下一步（无 BLOCK → /aisdd.gate implement-done；有 BLOCK → 修复或
  /aisdd.cr）

  └──────────────────────────┴──────────────────────────────────────────────┘

  ---
  测试任务的生成

  /aisdd.featuretasks 中有这句话：

  ▎ 测试任务可选：仅当功能规格中明确要求，或用户指定 TDD 
  方式时，才生成测试任务。

  意味着：
  - 测试代码的编写是可选的 Task
  - 即使写了测试，也没有命令自动运行这些测试并把结果反馈给流程

  ---
  这是一个真实缺口

  用 harness engineering 的视角看，这正是反馈环（feedback loop）不完整的地方：

  当前：  实现代码 → AI 静态阅读 → 主观判断"符合设计"
  完整的：实现代码 → 运行测试/lint/CI → 客观结果反馈回 agent loop

  OpenAI Codex 的 harness 把测试执行内嵌到 agent loop
  中——测试失败会自动触发下一轮修复。AISDD 目前没有这个闭环。

  ---
  当前可以手动补充的方式

  如果你想在现有流程中加入真实测试验证，需要：

  1. 在 tasks.md 中显式生成测试任务（featuretasks 时指定 TDD）
  2. 手动运行 ./gradlew test ���把结果反馈给 /aisdd.verify
  3. CI 结果目前不会自动进入 verify 流程
