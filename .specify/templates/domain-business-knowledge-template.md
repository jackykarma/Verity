# AI 时代领域业务文档模版

> **适用场景**：业务领域长期沉淀、跨 EPIC 复用、新人/onboarding、AI Agent 理解业务上下文、需求设计与影响分析前的领域对齐。
>
> **目标**：让领域知识不仅「人读得懂」，还能「AI 引得出、推得准、不幻觉」——作为 **Domain 级事实源**，支撑 spec / tech-spec / epic-design 的增量编写，而非替代它们。
>
> **存放位置**：项目 `/knowledge/02_domain_map/domains/domain_xxx.md`（单领域一份）；术语全局登记于 `/knowledge/00_system_charter/glossary.md`。
>
> **与其他文档的关系**：
>
> | 文档 | 粒度 | 关系 |
> |------|------|------|
> | 本模版（领域业务文档） | Domain 级、长期有效 | 描述「这个业务领域是什么、规则是什么」 |
> | `spec.md` / EPIC | Feature/迭代级 | 引用领域文档中的实体、规则、流程；不重复定义 |
> | `module_xxx.md` | Module 级 | 描述「如何实现」；归属本 Domain，互链索引 |
> | `glossary.md` | 全局术语 | 本领域专有名词须双向链接 |

## 0. AI 时代编写原则（必读）

### 0.1 为什么需要「AI 友好」的领域业务文档

领域知识传统上散落在 PRD、口头约定、老代码注释中，存在：**概念同名异义、规则隐含、边界模糊、跨域口径不一致**。在 AI 辅助需求分析与编码场景下，会导致：**错误补全业务规则、跨域调用假设、状态流转幻觉、指标口径编造**。

本模版要求领域文档同时服务两类读者：

| 读者 | 核心诉求 |
|------|----------|
| 人类（产品/研发/测试/运营/新人） | 快速建立领域心智模型，评审时有统一事实基线 |
| AI Agent | 结构稳定、编号可追溯、规则可解析、边界可判定 |

### 0.2 信息三级分类（编写时强制标注）

在正文或表格「来源」列标注信息可信度，**禁止把推断写成既定事实**：

| 标记 | 含义 | 写法要求 |
|------|------|----------|
| ✅ 已明确 | 业务评审或线上行为已确认 | 直接写入规则与定义 |
| ⚠️ 合理推断 | 根据代码/文档/访谈谨慎补全 | 须写明推断依据 |
| ❓ 待确认 | 缺失且影响设计/验收/协作 | 写入「待确认事项」，不得静默省略 |

### 0.3 编号与追溯规范

| 类型 | 编号前缀 | 示例 | 下游追溯 |
|------|----------|------|----------|
| 业务能力 | CAP- | CAP-001 | → Feature / EPIC / 模块职责 |
| 核心实体 | ENT- | ENT-001 | → 数据字典 / 接口字段 |
| 业务规则 | RULE- | RULE-001 | → spec FR / 校验逻辑 |
| 业务流程 | FLOW- | FLOW-001 | → 场景地图 / 时序图 |
| 业务场景 | S- | S-01 | → spec 场景 / 测试用例 |
| 跨域协作点 | X- | X-01 | → interface-design / 集成测试 |
| 风险 | R- | R-001 | → 项目风险管理 |
| 待确认 | O- | O-001 | → 评审 Action Item |

**追溯原则**：每条 RULE 须可关联到至少一个 CAP 或 ENT；跨域协作点 X-xx 须写明对端 Domain 与契约口径。

### 0.4 领域文档 vs 需求规格书（边界）

| 写入领域文档 | 不写入领域文档（放 spec/EPIC） |
|--------------|-------------------------------|
| 领域定位、长期目标、能力地图 | 单次迭代范围 In/Out |
| 实体定义、通用业务规则 | 具体页面字段、交互细节 |
| 标准流程与异常分支（领域级） | 本期新增/变更的功能点 AC |
| 跨域契约（业务语义） | 接口路径、类名、表结构 |
| 历史包袱、已知限制 | 排期、灰度、发布策略 |

领域文档变更频率低；**EPIC 级变更若影响领域规则，须回写本文件并升版本**。

### 0.5 人机协作工作流（建议）

```text
业务访谈 / 存量 PRD / 代码考古 → 领域业务文档（本模版）
    → glossary 登记 → module 互链 → spec/tech-spec 引用 CAP/RULE/ENT 编号
    → epic-design 落码设计 → 合入主干后回写领域文档
```
