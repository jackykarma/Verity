## Feature 拆分（EPIC → Feature）*（必填）*

> **拆分视角（首要原则）**：
>
> - Feature 从**业务场景 / 用户价值**视角拆分，不从技术架构 / 代码模块视角拆分。
> - 每个 Product Feature 应对应**用户可感知的一组业务能力或场景**。
> - Capability Feature 是**派生结果**——先识别 Product Feature，再看是否存在跨 Feature 复用需求，才考虑抽取为独立 Capability。
>
> **拆分标准（独立交付的含义）**：
>
> - **用户价值闭环**：交付后用户能独立使用该 Feature 并获得价值，不需要等待其他 Feature 完成才有意义。
> - **可独立验收**：可以定义出独立的验收标准，验收不依赖其他 Feature 的同时完成。
> - **边界清晰**：能明确回答"这个 Feature 包含什么、不包含什么"。
> - **粒度适中**：太大则失去拆分意义（一个 Feature 就是整个 EPIC），太小则碎片化（一个页面或一个接口一个 Feature）。
>
> **Feature 类型**：
>
> - `Product`：面向终端用户的业务功能，是拆分的**主体**。
> - `Capability`：从跨 Feature 复用需求中**派生**的共享能力（不区分偏业务还是偏技术），需满足升级条件才独立为 Feature。
>
> **反模式（禁止）**：
>
> - 不要按技术层拆分（如 UI Feature、数据层 Feature、网络层 Feature）。
> - 不要把一个技术组件直接当成 Feature，除非它满足 Capability 升级条件。
> - 不要拆出对用户无感知价值的 Product Feature。
> - 不要一上来就先拆 Capability，必须先从业务场景拆出 Product Feature，再识别共享需求。
>
> **工作流衔接**：
>
> - EPIC 可以记录**跨 Feature 的目标与统一约束**；单个 Feature 的可执行 FR/NFR 仍在各自 `spec.md` 中细化。
> - 本节输出用于后续逐个运行 `/aisdd.featurespec` 创建 Feature 文档目录与 spec.md（本工作流不为 Feature 创建 git 分支）。

## 跨 Feature 关注点与 Capability 决策 *（若存在则必填）*

> 说明：这里用于识别**跨 Feature 的共享关注点**，并决定它是否需要升级为独立的 Capability Feature。
>
> - 本节只做**识别与决策**，不展开接口、SDK、线程模型、预算分配等详细技术设计；这些内容在 `epic-plan.md` 或对应 Feature 文档中完成。
> - 若某关注点被升级为 Capability Feature，应同时出现在上方 Feature 列表中。
>
> 建议升级为 Capability Feature 的条件（满足其一即可）：
>
> - 被 2 个及以上 Feature 复用
> - 需要独立版本化、独立验收或独立发布节奏
> - 对多个 Feature 构成统一契约或高风险依赖
> - 存在明确的 Owner，需要先行设计、后续复用

## 跨 Feature 技术策略（轻量登记，详细约束下沉至 epic-plan）*（建议填写）*

> **目的**：在 EPIC 层做最小必要的协同登记，帮助后续 `epic-plan.md` 与各 Feature `plan.md` 明确复用关系和计划顺序。
>
> **时机**：建议在所有 Feature `spec.md` 完成后、运行 `/aisdd.epicplan` 前补齐；若前期已识别出明显共享项，也可先填写占位，后续与 `epic-plan.md` 对齐。
>
> **强制规则**：
>
> - 本节只登记**影响复用、Owner 和执行顺序**的信息；技术栈锁定、统一运行时原则、能力边界、预算分配等公共约束按需写入 `epic-plan.md`
> - 后续每个 Feature 在开始 plan 之前，**必须先阅读本章节**；若 EPIC 根下存在 `**epic-plan.md`**，**必须优先以 `epic-plan.md` 为准**
> - 若 Feature plan 中需要设计的共享组件已在此登记为“由其他 Feature 提供”，则应复用，不得重复设计
> - 若发现新的共享需求，必须先更新本章节，并在 `epic-plan.md` 中补齐对应详细约束

> 类型说明（共享能力的技术子类型，仅用于本登记表分类，不影响 Feature 类型）：
>
> - **Infrastructure**：基础设施与使能组件（UI 框架、数据层、网络层、错误处理、日志、配置等）
> - **Capability**：可被多个 Feature 复用、需要独立验收或版本化的业务/平台能力（是否独立为 Feature 由上一节决策）

## EPIC 完成条件 *（必填）*

> 说明：
>
> - EPIC 是 **Feature 的容器与编排单元**，不是额外的独立验收对象。
> - 每个 Feature 必须可独立验收、独立交付；EPIC 完成意味着其下必需 Feature 已完成并达到各自验收标准。
> - 若存在跨 Feature 的统一技术约束（如性能预算、隐私合规、可观测性口径），应登记在 `epic-plan.md` 或相应 Feature 文档中，而不是在此重复定义一套 EPIC 级 FR/NFR。

### 完成判定

- 所有 **必需** Feature 已完成并通过各自验收
- 依赖的 Capability Feature 已就绪并可被复用
- 各 Feature 间依赖关系已闭合，无阻塞交付的前置缺口
- 若存在跨 Feature 统一约束，已在 `epic-plan.md` 或相应 Feature 文档中落地并验证
- 上项范围内无阻塞发布的 P0/P1 级问题
