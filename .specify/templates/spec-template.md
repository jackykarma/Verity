## 完整场景矩阵 *（必填）*

> 说明：将核心用户旅程、边界与异常场景整合为结构化场景表，确保场景覆盖无遗漏。每条场景须关联至少一个 FR/NFR，便于下游设计走查（`epicdesign` 前置检查）与实现后验证（`verify`）追溯。
>
> **与上文「验收与场景」的关系**：上文用叙述体描述旅程与边界；本矩阵将其结构化并**补齐**上文未显式列出的场景类别。二者共同构成 spec 的场景事实源。
>
> **场景类别覆盖要求**：矩阵须覆盖以下全部类别（不适用的类别须保留行并在「场景名称」列标注 `N/A：[理由]`）：

| 类别 | 含义 | 必填条件 |
|------|------|----------|
| 正常流程 | 主干用户旅程的成功路径 | 始终必填 |
| 替代流程 | 达成同一目标的不同操作路径（如快捷操作、批量操作） | 存在多条路径时必填 |
| 边界值 | 输入/数据/状态的极端边界（最大、最小、空值、超长等） | 始终必填 |
| 异常/错误 | 网络失败、权限拒绝、数据异常、超时等错误场景 | 始终必填 |
| 并发/竞态 | 多处同时操作、快速重复操作、生命周期竞争 | 涉及异步/多入口时必填 |
| 生命周期 | 前后台切换、横竖屏旋转、进程被杀恢复、低内存回收 | 涉及 UI/状态持久化时必填 |
| 跨 Feature 集成 | 本 Feature 与其他 Feature 的交互场景 | 多 Feature EPIC 必填 |

| 场景ID | 类别 | 场景名称 | 前提条件 | 操作 | 预期结果 | 关联 FR/NFR | 优先级 |
|--------|------|----------|----------|------|----------|-------------|--------|
| SC-001 | 正常 | [场景名称] | [初始状态/前提] | [用户操作或系统触发] | [可验证的预期结果] | FR-001 | P0 |
| SC-002 | 边界 | [场景名称] | [边界条件描述] | [触发操作] | [预期行为/降级策略] | FR-002, NFR-REL-001 | P1 |
| SC-003 | 异常 | [场景名称] | [错误前提] | [触发操作] | [错误处理/恢复行为] | NFR-REL-001 | P0 |
| SC-004 | 跨Feature | [场景名称] | [涉及的 Feature 状态] | [跨 Feature 操作链] | [端到端预期结果] | FEAT-xxx/FR-001 | P1 |

> **优先级定义**：
> - **P0**：核心功能验收必须覆盖，不通过则 Feature 不可交付
> - **P1**：重要场景，需求评审或进入 Plan 前须确认覆盖情况
> - **P2**：增强场景，可在后续迭代中覆盖
>
> **完整性自检**：填写完成后，检查 §FR/NFR 中的每条 FR 是否至少被一条 P0/P1 场景覆盖；若存在未被任何场景覆盖的 FR，须补充场景或说明理由。
