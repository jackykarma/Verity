# PRD 评审

该 skill 的核心职责不是“帮产品整理功能方案”，而是站在研发评审视角，对产品给出的 PRD/需求文档做问题审查，尽可能找出所有会影响设计、开发、测试、验收和上线的问题点，并输出一份可直接拿去和产品逐条确认的“问题清单”。

## 目标

你需要完成的事情只有一类：

- 找出 PRD 中所有有问题的地方
- 找出所有不确定、模糊、歧义的描述
- 找出所有缺失但开发必须知道的信息
- 找出前后矛盾、逻辑冲突、边界遗漏、异常路径遗漏
- 输出结构化的问题列表，便于产品补充和澄清

## 不要做什么

除非用户明确要求，否则不要把重心放在以下内容上：

- 不要把主要篇幅用于“功能拆解”
- 不要输出大段“解决方案设计”
- 不要擅自补全产品意图并当成确定事实
- 不要把行业经验推断内容写成既定需求

如果必须做推断，必须明确标注：`这是推断，不是 PRD 明确说明`

## 输入形式

支持以下任一输入：
- PRD 文档链接（如 Confluence、Notion、飞书文档）
- 需求描述文本
- 产品经理口述整理

## 核心输出

输出必须以“问题清单”为中心，而不是以“功能清单”为中心。最终产物至少包含：

- 问题编号
- 问题类型
- 问题优先级
- 原文依据或对应描述
- 问题说明
- 为什么这是问题
- 影响范围
- 需要产品补充/确认的内容
- 建议向产品追问的问题

## 分析流程

### 步骤 1：获取需求原文

**如果是文档链接**：
- 使用 `WebFetch` 获取文档内容
- 如果无法访问，明确告知并要求用户提供文档文本

**如果是文本描述**：
- 直接解析原文
- 如果文本明显不完整，先指出“分析结论会受限”

### 步骤 2：快速建立需求上下文

先用 3-5 句话总结，不求完整，只求帮助后续审查：

- 这个需求要解决什么问题
- 谁在使用
- 核心动作是什么
- 影响哪些页面/模块/角色
- 成功标准大概是什么

注意：这一步只是为了建立审查上下文，不是最终交付重点。

### 步骤 3：逐维度审查 PRD 问题

按以下维度系统检查，尽量做到“一个维度一个维度扫过去”，不要漏：

#### 3.1 背景与目标

- 需求背景是否说清
- 目标是否可判断是否达成
- 是否缺少业务动机、价值说明
- 是否存在“为了优化体验”但没有定义优化指标

#### 3.2 范围与边界

- 做什么写了，什么不做是否写清
- 是否缺少适用范围、非适用范围
- 是否缺少入口、出口、前置条件、终止条件
- 是否缺少边界条件说明

#### 3.3 用户、角色与权限

- 谁可以使用是否明确
- 不同角色差异是否明确
- 是否有权限控制但未给规则
- 是否遗漏管理员/运营/普通用户等不同视角

#### 3.4 业务规则

- 触发条件是否清楚
- 处理规则是否清楚
- 优先级、排序、去重、覆盖、失效规则是否明确
- 是否使用了“合理”“适当”“尽快”“相关”等模糊词
- 是否存在多个理解口径

#### 3.5 数据定义与口径

- 字段含义是否明确
- 数据来源是否明确
- 新增/修改/删除的数据项是否完整
- 展示口径、统计口径、时间口径是否一致
- 是否缺少枚举值、单位、格式、精度、默认值

#### 3.6 交互与流程

- 主流程是否完整
- 是否缺少异常流程、取消流程、返回流程
- 是否遗漏空状态、加载态、失败态、无权限态
- 是否缺少用户操作反馈
- 页面跳转、弹窗、提示文案是否清楚

#### 3.7 异常与边界场景

- 网络异常怎么处理
- 数据为空怎么处理
- 重复提交怎么处理
- 并发/冲突/过期/回退怎么处理
- 超长文本、极值、非法输入、老数据兼容是否说明

#### 3.8 依赖与约束

- 是否依赖其他团队、接口、配置、活动、策略
- 外部依赖是否已经就绪
- 是否有版本限制、灰度限制、平台限制
- 是否缺少上线条件和协作前提

#### 3.9 验收标准

- 是否能判断“做完算成功”
- 是否有可验证、可测试、可回归的标准
- 是否存在“主观验收”而非“客观验收”
- 是否缺少埋点、日志、监控、风控等验收配套

#### 3.10 一致性与冲突

- 前后描述是否矛盾
- 术语是否统一
- 图文是否一致
- 与现有产品逻辑是否冲突
- 一个地方说 A，另一个地方像是在说非 A

### 步骤 4：归类问题

将识别到的问题归入以下常见类型：

- `信息缺失`：开发必须知道，但 PRD 没写
- `描述模糊`：写了，但表述不明确
- `存在歧义`：同一句话可能有多种理解
- `逻辑冲突`：前后描述不一致或规则相互打架
- `边界遗漏`：极端/异常/取消/回退等场景没写
- `角色权限不清`：谁能做、谁不能做没有说清
- `数据口径不清`：字段、来源、单位、计算口径不明确
- `验收缺失`：无法判断需求是否完成
- `依赖待确认`：依赖外部条件但未明确
- `风险项`：即使 PRD 写了，但落地风险高，需要提前确认

### 步骤 5：按优先级排序

优先级建议如下：

- `高`：不确认就无法设计、开发、测试或会导致方向错误
- `中`：可以继续推进，但后续大概率返工
- `低`：不影响主链路，可在详细设计或联调前确认

优先级排序原则：

- 先排“会阻塞开发”的问题
- 再排“会导致返工”的问题
- 最后排“体验细节类”的问题

### 步骤 6：生成问题清单文档

使用以下模板输出：

```markdown
# [功能名称] PRD 评审

> 分析时间：YYYY-MM-DD
> 需求来源：[PRD 链接/口述整理]

## 1. 需求概览

- 目标一句话总结：[简述该需求想解决什么问题]
- 影响范围：[页面/模块/角色]
- 当前判断：[需求可理解程度，高/中/低]

---

## 2. 关键问题清单

| 编号 | 类型 | 优先级 | 原文/依据 | 问题描述 | 为什么是问题 | 影响范围 | 需产品明确内容 | 建议追问 |
|------|------|--------|-----------|----------|----------------|----------|------------------|----------|
| Q-001 | 信息缺失 | 高 | [引用原文或写“PRD 未提及”] | [缺了什么] | [为什么缺失会阻塞] | [影响设计/开发/测试/上线] | [需要补充什么] | [建议怎么问产品] |
| Q-002 | 描述模糊 | 高 | "[原文]" | [哪里模糊] | [可能有几种理解] | [会导致什么分歧] | [要明确哪个口径] | [建议问题] |
| Q-003 | 逻辑冲突 | 中 | "[原文 A]" + "[原文 B]" | [冲突点] | [为什么矛盾] | [会影响什么] | [以哪个规则为准] | [建议问题] |

---

## 3. 按类别汇总

### 3.1 高优先级问题

- [Q-001] [一句话概述]
- [Q-002] [一句话概述]

### 3.2 中优先级问题

- [Q-00X] [一句话概述]

### 3.3 低优先级问题

- [Q-00X] [一句话概述]

---

## 4. 缺失主题检查

若 PRD 完全未覆盖但通常必须明确，可列出：

- 角色与权限：[是否缺失]
- 数据定义：[是否缺失]
- 状态与异常处理：[是否缺失]
- 验收标准：[是否缺失]
- 外部依赖：[是否缺失]

---

## 5. 建议与下一步

- 建议先与产品确认的 Top 3 问题：
1. [问题 1]
2. [问题 2]
3. [问题 3]

- 建议补充到 PRD 的内容：
  [列出建议补充的章节或字段]

---

## 6. 说明

- 显式信息：[来自原文的明确表述]
- 推断信息：[基于上下文的推断，需单独标注]
- 本文目标：帮助产品补全文档、帮助研发减少返工，不代表最终方案设计
```

## 输出要求

将生成的文档保存至：
- 如有明确需求名：`docs/requirements/[feature-name]-prd-review.md`
- 如无明确名称：询问用户命名偏好

输出时必须遵守以下要求：

- 所有问题尽量引用 PRD 原文，避免“空口判断”
- 每个问题都要说明“为什么这是问题”
- 每个问题都要说明“需要产品确认什么”
- 优先输出真正阻塞研发的问题，不要只挑措辞问题
- 如果某项是推断出来的问题，要明确写明“基于推断”
- 如果 PRD 整体质量较好，也要明确写出“未发现明显问题”的范围和前提

## 快速输出模式

如果用户只要一个简短版，可输出：

```markdown
# [功能名称] PRD 问题清单（精简版）

## 结论
- 当前 PRD 主要问题数：[X]
- 高优先级问题数：[X]
- 当前是否足够进入开发：[可以 / 不建议]

## 待确认问题
1. [高] [问题]
2. [高] [问题]
3. [中] [问题]
4. [中] [问题]
5. [低] [问题]

## 建议
- 建议产品先补充：[最关键缺失项]
```

## 参考资源

审查时可参考 [prd-template.md](prd-template.md) 了解一份完整 PRD 应具备的标准章节与字段，以此判断被审查文档有哪些章节或内容缺失。

## 使用提示

- 当用户说“分析需求”“评审 PRD”“找出问题”“列待确认项”“梳理不清楚的地方”时，优先使用本 skill
- 如果用户同时要求“把 PRD 转成正式规格书”，应考虑改用 `requirement-spec-generator`
- 如果用户要求“做技术方案/架构设计”，应考虑改用 `design-solution`

## 输出质量检查

- [ ] 是否以“问题清单”为核心而不是功能列表
- [ ] 是否覆盖缺失、模糊、歧义、冲突、边界、异常、验收、依赖
- [ ] 是否标注原文依据或明确说明“PRD 未提及”
- [ ] 是否给出了优先级
- [ ] 是否说明了影响范围
- [ ] 是否给出了建议向产品确认的问题
