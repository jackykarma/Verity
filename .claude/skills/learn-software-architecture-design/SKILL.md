# 软件系统架构设计学习

围绕软件系统架构设计主题输出可学习文档，帮助用户建立"问题、边界、分层、职责、协作、权衡、落地"的系统认知。

---

## 学习方法

始终遵循以下方法：

1. 先激活已有的设计经历和遇到过的设计问题，再建立系统方法论。
2. 先理解为什么要做架构设计，再学习如何设计。
3. 先看系统边界和上下文，再进入模块、类和接口细节。
4. 用用户自己提出的问题和设计困惑驱动学习，内容围绕这些问题展开。
5. 用费曼式表达检验理解——能讲清楚某个设计决策的权衡才算真懂。
6. 用主动回忆和生成效应（先猜后看）固化设计思维。
7. 用间隔复习对抗遗忘，并通过对照真实代码强化迁移。
8. 用分层递进学习：方法论 -> 0 层 -> 1 层 -> 2 层 -> 对象设计 -> 演进治理。

---

## 问题前置：学习前先提问（子主题级必做）

**这是最重要的一步，不可省略。**

当用户明确了要学的子主题时，在生成任何学习内容之前，必须先进入"问题前置"环节。

### 问题前置的目的

- 激活用户已有的设计经验，避免从零灌输用户已知的内容
- 把用户真实遇到的设计困境转化为学习主线
- 为后续"验收"提供基准：学完后回头看，哪些问题答了、哪些还没答

### 如何提问

围绕主题，从以下维度主动向用户提问，问题数量不设上限，覆盖所有对学习有价值的角度：

**1. 已有认知探底**
- 你对这个主题目前了解多少？
- 你做过架构设计或详细设计吗？大概是什么规模的系统？
- 你能描述一下你现在设计的方式或习惯吗？

**2. 问题与困惑收集**
- 你最想搞清楚的是什么？
- 你在设计时遇到过什么具体的困难——比如不知道怎么分层、怎么划边界、怎么画图？
- 有没有你做过回头觉得"这个设计真的很烂"的经历？
- 有没有"这两个概念/方法我总搞混"的疑问？

**3. 学习目标锚定**
- 学完这个主题，你希望能做到什么？（能画出清晰的架构图？能做详细设计？能评审别人的设计？）
- 你是为了当前某个项目的设计任务，还是系统提升设计能力？
- 学完后你打算做什么设计练习或验证？

**4. 场景与背景锚定**
- 你目前在做什么系统或功能？这个主题和它有关系吗？
- 你最近遇到了什么设计上的困惑或争议？

**5. 主题专属深挖问题**

根据具体主题补充针对性问题，以下是常见主题示例，实际执行时应根据主题动态生成：

- **0 层架构设计**：你知道 0 层架构图要回答什么问题吗？你画过系统上下文图吗？你知道系统边界和外部依赖怎么识别吗？
- **DDD**：你知道 DDD 是什么缩写吗？你知道限界上下文是什么吗？你知道实体和值对象的区别吗？你遇到过领域模型混乱的问题吗？
- **模块划分**：你知道如何判断两个功能应不应该放在同一个模块吗？你遇到过模块职责不清、相互依赖混乱的情况吗？你知道高内聚低耦合怎么在实际中落地吗？
- **接口设计**：你知道好的接口设计有哪些标准吗？你遇到过接口设计不合理导致调用方很难用的情况吗？你知道接口稳定性和扩展性如何权衡吗？
- **SOLID**：你知道 SOLID 五个原则各是什么吗？你遇到过违反某个原则导致代码很难维护的情况吗？
- **架构评审**：你做过架构评审吗？你知道评审时应该关注什么吗？你遇到过评审走过场没发现问题的情况吗？

**提问格式要求**：

把所有问题一次性列出，编号呈现。不要分批问，等用户统一回答后再继续。示例：

```
在开始之前，我想先了解你对这个主题的认知和经历，帮我生成更贴合你需求的学习内容：

1. 你对 DDD 目前了解多少？有没有在项目里用过？
2. 你最想搞清楚的是什么？
3. 你知道限界上下文（Bounded Context）是什么吗？
4. 你知道实体和值对象的区别吗？
5. 你遇到过领域模型混乱、到处都是贫血模型的情况吗？
6. 你知道 DDD 和传统三层架构的区别吗？
7. 你是为了当前项目的设计重构，还是系统学习？
8. 你目前做的是什么类型的系统？
9. ...（根据主题继续补充）

请直接回答你知道的，不知道的就说不知道，有实际经历也可以分享。
```

### 收到用户回答后

根据用户的回答做以下处理：

1. **识别起点**：用户已经知道什么，不需要从零讲
2. **提炼问题清单**：把用户说出的困惑和想搞清楚的问题整理成"本次学习的问题清单"
3. **调整内容侧重**：用户不懂的地方多讲，已懂的快速确认或跳过
4. **在文档开头放问题清单**：作为学习主线，并在结尾逐一检验

- 子主题级输入：先进入问题前置环节，再生成内容

## 输入要求

至���明确以下信息；如果用户未明确补充，则使用默认行为：

- 输入层级：`领域` 或 `子主题`

如果主题过大，优先缩小到一个设计层次、一个方法或一个典型问题。

## 输出策略

先判断当前输入属于哪一层：

### 领域级输入

当用户输入的是领域而不是单一主题时，先输出 1 篇 `领域学习地图.md`，不要直接展开多个子主题正文。

`领域学习地图.md` 必须包含：

- 这个领域在学什么
- 为什么值得学
- 适合什么目标的人学习
- 前置知识
- 知识树或主题树
- 推荐学习顺序
- 子主题分级与标签
- 每个子主题解决什么问题
- 哪些主题适合先学
- 下一步可选输出主题

学习地图中的每个子主题都尽量标注以下信息：

- 难度：`入门`、`进阶`、`深入`
- 优先级：`建议优先`、`按需学习`、`可后置`
- 适合目标：如"建立架构观""会做系统分层""会做详细设计"
- 前置知识：进入该主题前最好先掌握什么
- 是否可跳过：`否`、`部分可跳过`、`可跳过`
- 产出收益：学完后能解决什么问题

如果用户没有指定子主题，就停在学习地图这一层，等待用户选择下一步。

### 子主题级输入

当用户输入的是明确子主题，如 `0 层架构设计`、`DDD`、`面向对象设计`、`接口设计`，先进入问题前置环节，再根据深度输出 `主题总览.md` 或多篇学习包。

## 文件命名与配图要求

- 所有学习文档统一输出到 `docs/learn/软件系统架构设计/` 目录下。
- 领域级文档默认保存为 `docs/learn/软件系统架构设计/领域学习地图.md`。
- 子主题级文档必须按主题创建子目录，保存到 `docs/learn/软件系统架构设计/[子主题名]/` 下。
- `quick` 模式默认保存为 `docs/learn/软件系统架构设计/[子主题名]/主题总览.md`。
- `deep` 模式默认保存为 `docs/learn/软件系统架构设计/[子主题名]/` 下的多篇结构化文档。
- 输出的 Markdown 文件名必须使用中文，不使用英文语义文件名。
- 文件名可以包含数字前缀以表达学习顺序，如 `00-学习地图.md`、`01-背景与核心方法论.md`。
- 图示默认优先使用 Mermaid，尤其适用于上下文图、分层图、模块图、类图、时序图、流程图、演进图和时间线。
- 当 Mermaid 难以表达成熟框架图、经典架构示意图或权威教学图时，可以从网络抓取图片辅助讲解。
- 使用网络图片时，必须在文档中标注来源链接、图片用途，并简要说明该图片帮助理解什么。
- 对来源不明、版权不清晰、内容失真或营销性质过强的图片，不要使用；此时退回 Mermaid 或文字说明。

## 通用写作要求

每篇文档都应尽量包含：

- 一句话理解
- 这个设计主题解决什么问题
- 背景与演进
- 适用边界
- 关键方法或步骤
- 一个真实或典型案例
- 常见误区
- 自测题

不要只讲概念名词。必须讲清楚这个方法在什么上下文下有价值，解决什么矛盾，以及代价是什么。
