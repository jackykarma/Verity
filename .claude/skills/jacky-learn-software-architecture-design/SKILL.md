# 软件系统架构设计学习

围绕软件系统架构设计主题输出可学习文档，帮助用户建立“问题、边界、分层、职责、协作、权衡、落地”的系统认知。

## 学习方法

始终遵循以下方法：

1. 先理解为什么要做架构设计，再学习如何设计。
2. 先看系统边界和上下文，再进入模块、类和接口细节。
3. 先学设计思路和权衡，再学图和文档模板。
4. 用案例驱动学习，避免把架构方法论学成口号。
5. 用分层递进学习：方法论 -> 0 层 -> 1 层 -> 2 层 -> 对象设计 -> 演进治理。
6. 每篇结尾必须有自测题、复述任务或小型设计练习。

## 默认行为

如果用户只输入一个领域或主题，没有补充更多要求，默认按以下规则执行：

- 学习程度默认使用 `系统深入`
- 学习目标默认包含：`能讲给别人听`、`能实战`、`能画图`
- 输出要求默认使用：`先生成学习地图`

因此，除非用户显式修改，否则不需要反复追问“学到什么程度”“学习目标是什么”“是否先出学习地图”。

## 输入要求

至少明确以下信息；如果用户未明确补充，则使用默认行为：

- 输入层级：`领域` 或 `子主题`
- 学习主题：如 `DDD`、`0 层架构设计`、`模块划分`、`接口设计`、`领域建模`
- 学习深度：默认 `deep`
- 学习目标：默认是“能讲给别人听、能实战、能画图”

如果输入的是大领域，如 `软件系统架构设计`、`架构设计方法论`、`系统设计`，不要直接展开多篇正文，先产出学习地图，再让用户选择子主题。
如果主题过大，优先缩小到一个设计层次、一个方法或一个典型问题。

## 输出策略

先判断当前输入属于哪一层：

### 领域级输入

当用户输入的是领域而不是单一主题时，先输出 1 篇 `领域学习地图.md`，不要直接展开多个子主题正文。

`领域学习地图.md` 必须包含：

- 这个领域在学什么
- 为什么值得学
- 适合什么目标的人学习
- 前置知识
- 知识树或主题树
- 推荐学习顺序
- 子主题分级与标签
- 每个子主题解决什么问题
- 哪些主题适合先学
- 下一步可选输出主题

学习地图中的每个子主题都尽量标注以下信息：

- 难度：`入门`、`进阶`、`深入`
- 优先级：`建议优先`、`按需学习`、`可后置`
- 适合目标：如“建立架构观”“会做系统分层”“会做详细设计”
- 前置知识：进入该主题前最好先掌握什么
- 是否可跳过：`否`、`部分可跳过`、`可跳过`
- 产出收益：学完后能解决什么问题

如果用户没有指定子主题，就停在学习地图这一层，等待用户选择下一步。

### 子主题级输入

当用户输入的是明确子主题，如 `0 层架构设计`、`DDD`、`面向对象设计`、`接口设计`，再根据深度输出 `主题总览.md` 或多篇学习包。

## 输出模式

以下模式仅适用于“已经明确子主题”的情况：

### `quick`

输出 1 篇 Markdown 文档，帮助用户快速建立主题认知和设计边界。文件名必须使用中文，默认使用 `主题总览.md`。

### `deep`

输出 3~6 篇 Markdown 文档，组成学习包。文件名必须使用中文。默认建议文件：

- `00-学习地图.md`
- `01-背景与核心方法论.md`
- `02-分层架构与设计视角.md`
- `03-关键设计方法与案例.md`
- `04-常见陷阱与评审要点.md`
- `05-自测与延伸学习.md`

## 文件命名与配图要求

- 所有学习文档统一输出到 `docs/learn/软件系统架构设计/` 目录下。
- 领域级文档默认保存为 `docs/learn/软件系统架构设计/领域学习地图.md`。
- 子主题级文档必须按主题创建子目录，保存到 `docs/learn/软件系统架构设计/[子主题名]/` 下。
- `quick` 模式默认保存为 `docs/learn/软件系统架构设计/[子主题名]/主题总览.md`。
- `deep` 模式默认保存为 `docs/learn/软件系统架构设计/[子主题名]/` 下的多篇结构化文档。
- 输出的 Markdown 文件名必须使用中文，不使用英文语义文件名。
- 文件名可以包含数字前缀以表达学习顺序，如 `00-学习地图.md`、`01-背景与核心方法论.md`。
- 图示默认优先使用 Mermaid，尤其适用于上下文图、分层图、模块图、类图、时序图、流程图、演进图和时间线。
- 当 Mermaid 难以表达成熟框架图、经典架构示意图或权威教学图时，可以从网络抓取图片辅助讲解。
- 网络图片优先选择官方文档、权威技术博客、经典教材配图、大学课程资料或架构领域权威资源中的图片。
- 使用网络图片时，必须在文档中标注来源链接、图片用途，并简要说明该图片帮助理解什么。
- 对来源不明、版权不清晰、内容失真或营销性质过强的图片，不要使用；此时退回 Mermaid 或文字说明。

## 通用写作要求

每篇文档都应尽量包含：

- 一句话理解
- 这个设计主题解决什么问题
- 背景与演进
- 适用边界
- 关键方法或步骤
- 一个真实或典型案例
- 常见误区
- 自测题

不要只讲概念名词。必须讲清楚这个方法在什么上下文下有价值，解决什么矛盾，以及代价是什么。

## 领域专用模块

软件系统架构设计主题优先补充以下内容：

- 业务边界、系统边界、外部依赖
- 0 层、1 层、2 层设计视角及其关系
- 模块职责、接口边界、数据流和依赖方向
- 面向对象建模、聚合、实体、值对象、领域服务
- 设计原则、设计模式、设计权衡
- 架构评审、演进治理、可扩展性和可维护性

## 核心主线：从需求到架构设计

当主题涉及“如何从需求一步步推导出架构设计”时，优先沿着下面这条主线展开，不要把 0 层、1 层、2 层设计拆成互不关联的知识点。

### 设计递进链路

始终按以下顺序组织内容：

1. 需求输入与问题澄清
2. 业务边界与系统边界识别
3. 0 层架构设计
4. 1 层架构设计
5. 关键模块设计
6. 2 层详细设计
7. 图表表达与设计文档化
8. 评审、收敛与迭代

### 每一步必须回答的问题

#### 1. 需求输入与问题澄清

- 这个需求真正要解决什么问题
- 用户是谁，场景是什么
- 输入输出是什么
- 成功标准是什么
- 有哪些约束和非目标

#### 2. 业务边界与系统边界识别

- 系统自己负责什么
- 外部系统负责什么
- 本次设计覆盖什么，不覆盖什么
- 哪些能力是核心域，哪些是支撑域

#### 3. 0 层架构设计

- 系统在更大业务环境中的位置
- 上下游系统和交互关系
- 系统边界和外部依赖
- 核心输入输出与主业务流

#### 4. 1 层架构设计

- 系统内部如何分层与分模块
- 每个模块的职责是什么
- 模块之间如何协作
- 数据流、调用流如何流动

#### 5. 关键模块设计

- 哪些模块是高复杂度、高风险或高价值模块
- 这些模块的输入输出、状态和扩展点是什么
- 模块边界为什么这样划分

#### 6. 2 层详细设计

- 类、接口、实体、聚合如何建模
- 主流程和异常流程如何协作
- 数据结构、状态机、错误处理如何设计

#### 7. 图表表达与设计文档化

- 哪些内容适合用上下文图
- 哪些内容适合用分层图、类图、时序图、流程图
- 图表如何和文字解释互相补充

#### 8. 评审、收敛与迭代

- 设计是否满足质量属性目标
- 是否存在职责不清、边界不清、过度设计
- 实现成本和收益是否匹配

### 输出要求

如果用户学习的是这条主线，输出内容必须显式体现“从前一步如何推到后一步”，而不是平铺式介绍术语。

优先产出：

- 一条完整的设计递进链路
- 每一层设计的关注点、输入、输出和产物
- 一个从需求逐步推到详细设计的案例
- 对应的图表示例和画图时机

## 领域质量标准

生成内容时必须做到：

- 区分方法论、架构层次、实现细节，不混在一起讲。
- 对 0 层、1 层、2 层设计，必须讲清楚关注点、产物和边界。
- 对 DDD 和面向对象设计，必须讲清楚适用场景和常见误用。
- 讲架构时必须补充质量属性和设计权衡，避免只有“最佳实践”没有代价。
- 如果涉及图表，优先输出真实可用的上下文图、分层图、类图、时序图和流程图。

## 结尾要求

结尾固定给出：

- 这次学习最值得记住的 3 句话
- 1~3 个适合动手的小型设计练习
- 下一步建议：继续学什么方法、画什么图、拆什么案例

如果当前输出的是 `领域学习地图.md`，则把结尾改为：

- 建议先学的 1~3 个子主题
- 每个子主题适合的学习目标
- 等待用户选择下一步要展开的主题
