## 背景与价值

- **背景**：现有 Android 应用的图片浏览方案在超大图加载（2 亿像素级）、多格式兼容（HEIF/WebP/GIF 等）以及手势交互流畅度方面存在明显短板，高像素图片加载时频发 OOM，手势操作在中低端设备上掉帧严重，严重影响用户体验。
- **目标**：在 Android 媒体浏览 SDK 中提供生产级图片浏览核心能力，使接入方能够以最小成本集成高性能图片查看器，支持主流图片格式解码、超大图分块渲染，以及完整的手势交互体系。
- **价值**：
  - 用户价值：用户可流畅查看任意格式、任意像素规模的图片，通过自然手势操控图片，无卡顿、无模糊、无崩溃。
  - 业务价值：SDK 化交付降低接入成本，接入方无需自行实现复杂的分块解码与手势系统。
  - 平台价值：作为 EPIC-001 的核心基础能力，后续 Pager 翻页（FEAT-002）、幻灯片（FEAT-007）等 Feature 均依赖本 Feature 的图片渲染��手势体系。
- **范围（In Scope）**：
  - 多格式静态图片解码：JPEG、PNG（含透明通道）、HEIF/HEIC（Android 9+ 硬件解码）、WebP（含动态 WebP）、BMP
  - GIF 动图解码与按帧率自动播放（进入视口后触发）
  - 超大图分块（Tile）加载与视口区域按需解码，支持 2 亿像素级图片，不 OOM
  - 放大后对应区域 Tile 重新解码，保证任意缩放倍率下无拉伸模糊
  - 双击放大（相对当前倍率 2 倍；已达 5× 上限则不响应）
  - 双指无极捏合缩放，范围 [1×, 5×]，超限有橡皮筋阻尼，松手回弹
  - 单指平移（内容超出视口时可用），边缘过界后松手回弹
  - 双指旋转（图片跟随实时旋转），松手后自动对齐到最近 90° 倍数，含对齐动画
  - 加载中显示 loading 状态；加载失败显示 error placeholder（样式由接入方定义）
  - 内存不足时自动释放低优先级 Tile 缓存，降级解码精度
  - Tile 大小、内存缓存上限、解码线程数可通过 SDK 配置，SDK 提供合理默认值
- **范围外（Out of Scope）**：
  - 视频播放（属于 FEAT-003）
  - 实况图动效（属于 FEAT-004）
  - HDR 渲染（属于 FEAT-005）
  - Pager 翻页容器（属于 FEAT-002）
  - error placeholder 的默认 UI 样式（完全由接入方实现）

## 依赖关系

- **上游依赖**：
  - 图片加载框架：由接入方注入（Glide / Coil 或其他兼容框架），支持网络 URL、本地文件路径、ContentResolver URI 三类数据源；SDK 通过统一的数据源接口与之交互，不绑定具体框架实现。
  - 系统区域解码能力：Android 系统原生提供，SDK 仅调用其公开接口完成超大图的分块区域解码；最低兼容 Android 8.0（API 26），HEIF 解码需 Android 9.0（API 28）。
- **下游影响**：
  - FEAT-002（Pager 翻页容器）：直接复用本 Feature 的图片渲染与手势体系；本 Feature 的手势接口设计需预留与 Pager 水平滑动手势的冲突消解扩展点。
  - FEAT-007（幻灯片）：依赖本 Feature 的图片加载与渲染能力。
  - FEAT-009（事件回调）：依赖本 Feature 暴露的缩放、点击等状态事件。
- **外部依赖故障模式**：
  - 图片加载框架返回解码失败：SDK 触发 error placeholder 展示，通过回调通知接入方，不崩溃。
  - 系统区域解码能力在特定设备上不可用（如厂商定制 ROM 裁剪）：SDK 降级为全图解码并按缩放比例采样，超大图降级时日志告警，保证功能可用性但可能牺牲清晰度。
  - 图片文件损坏或格式不识别：SDK 判定解码失败，展示 error placeholder，通过回调上报错误类型，不崩溃。
  - 网络图片加载超时：由接入方注入的加载框架负责超时处理，SDK 维持 loading 状态直至收到成功/失败回调。

## 验收与场景

> 说明：本节用于"可测试"的需求验收；不等同于技术 Story（技术 Story 在 Plan 阶段拆分）。

### 核心用户旅程

#### 旅程 1 - 普通图片浏览与手势操控

- **描述**：用户打开图片查看器浏览一张普通 JPEG/PNG/HEIF/WebP/BMP/GIF 图片，通过双击、捏合、平移、旋转等手势自由操控图片，完成查看后退出。
- **成功信号**：图片无闪烁地加载完成并清晰展示；手势操控全程流畅，无明显卡顿；旋转松手后整齐对齐到最近 90° 倍数；GIF 动图按原始帧率播放。
- **验收场景**：
  1. **前提** 查看器以网络 URL 形式加载一张 8MP JPEG 图片，**当** 图片加载完成，**则** 图片完整清晰地填充到查看器容器，无拉伸变形，loading 状态消失。
  2. **前提** 图片已展示在 1× 缩放状态，**当** 用户双击图片，**则** 图片放大到 2× 并以点击位置为中心；再次双击后图片回到 1×。
  3. **前提** 图片处于 3× 放大状态，**当** 用户单指向左拖动，**则** 图片随手指平移，到达内容左边缘后继续拖动有阻尼感，松手后回弹到合法范围内。
  4. **前提** 图片处于 1× 状态，**当** 用户双指旋转约 60°，**则** 松手后图片自动以动画对齐到 90° 位置。
  5. **前提** 查看器加载一张本地 GIF 动图，**当** 查看器完全进入视口，**则** GIF 按原始帧率开始自动播放；当查看器离开视口，**则** GIF 停止播放。

#### 旅程 2 - 超大图浏览（2 亿像素级）

- **描述**：用户打开一张 2 亿像素级的超大 JPEG 图片，SDK 自动按视口区域分块加载，用户通过捏合放大到高倍率后仍能看到清晰细节，全程内存占用不超过系统限制，不发生 OOM。
- **成功信号**：图片在合理时间内呈现可交互状态（先展示低分辨率预览，再按需加载高清 Tile）；放大至任意倍率后对应区域 Tile 完成重解码，无模糊；设备内存不足时自动降级，不崩溃。
- **验收场景**：
  1. **前提** 查看器加载一张 2 亿像素 JPEG 图片，**当** 图片加载开始，**则** 立即展示 loading 状态；图片首帧可交互（低分辨率预览）出现后 loading 状态消失。
  2. **前提** 超大图处于 1× 状态，**当** 用户捏合放大到 5×，**则** 当前视口范围内对应 Tile 重新以高清精度解码并渲染，无可见模糊；视口外的 Tile 不主动解码。
  3. **前提** 设备可用内存紧张（模拟 onLowMemory），**当** 用户继续操控超大图，**则** SDK 自动释放低优先级 Tile 缓存，解码精度可降级，但查看器不崩溃、不黑屏。
  4. **前提** 在 4GB RAM 设备上加载 2 亿像素 JPEG，**当** 用户完成从 1× 放大至 5× 再缩小至 1× 的完整操作，**则** 全程不发生 OOM（通过 Profiler 内存监控验证）。

### 边界与异常场景

- **格式不支持**（非 JPEG/PNG/HEIF/WebP/BMP/GIF 的文件，如 TIFF、RAW）→ SDK 判定解码失败，展示接入方定义的 error placeholder，通过错误回调上报"不支持的格式"，不崩溃。
- **文件损坏**（图片文件头损坏或数据截断）→ SDK 解码失败，展示 error placeholder，回调上报"文件损坏"错误，不崩溃。
- **加载超时**（网络图片长时间未返回）→ loading 状态持续展示，超时处理由接入方注入的加载框架负责；加载框架回调失败后 SDK 展示 error placeholder。
- **内存不足**（系统触发 onLowMemory）→ SDK 自动释放低优先级 Tile 缓存，必要时降级解码精度，不崩溃，不产生 ANR。
- **快速连续手势**（如极快速度连续双击或快速捏合到边界）→ 所有手势状态机正确收敛，不产生状态错乱；缩放倍率始终保持在 [1×, 5×] 合法范围内（含阻尼区间）。
- **超过缩放上限（5×）时继续捏合**→ 有明显橡皮筋阻尼感，松手后自动回弹到 5×，不超限。
- **低于缩放下限（1×）时继续缩小**→ 有阻尼感，松手后回弹到 fit-screen（1×），不超限。
- **图片未放大时尝试平移**→ 平移手势不响应（内容未超出视口，无平移必要）；仅当内容超出视口时才响应平移。
- **快速连续切换图片 100 次**（适用于与 FEAT-002 集成后的场景）→ 不发生崩溃，内存无持续增长。
- **HEIF 解码在 Android 8.0 设备（API 26）上调用**→ SDK 检测系统版本，在不支持硬件 HEIF 解码的设备上回退到软解或展示 error placeholder（视设备能力而定），不崩溃。

## FR / NFR

### FR（Functional Requirements）

- **FR-001**：系统必须能够解码并渲染 JPEG 格式图片（含渐进式 JPEG）。
- **FR-002**：系统必须能够解码并渲染 PNG 格式图片，包括含 Alpha 透明通道的 PNG。
- **FR-003**：系统必须能够在 Android 9.0（API 28）及以上设备上解码并渲染 HEIF/HEIC 格式图片；在不支持的设备上回退到 error placeholder 或软解（若系统提供软解能力）。
- **FR-004**：系统必须能够解码并渲染静态 WebP 和动态 WebP 格式图片。
- **FR-005**：系统必须能够解码并渲染 BMP 格式图片。
- **FR-006**：系统必须能够解码 GIF 动图，并在图片进入视口后按原始帧率自动播放；图片离开视口后停止播放。
- **FR-007**：系统必须支持 2 亿像素级图片的分块加载与区域按需解码；任意时刻只对当前视口所在 Tile 区域执行解码，视口外区域不主动解码。
- **FR-008**：系统必须在图片放大后，对当前视口范围内的 Tile 以对应倍率重新解码，不允许以拉伸方式替代高清解码（即任意缩放倍率下不可出现明显模糊）。
- **FR-009**：用户必须能够通过双击手势放大图片；双击时放大倍率为当前倍率的 2 倍，以点击位置为放大中心；当已达 5× 上限时，双击不再放大。
- **FR-010**：用户必须能够通过双指捏合手势对图片进行无极缩放，缩放范围限制在 [1×, 5×]；超出范围时有橡皮筋阻尼效果，松手后自动回弹到边界值。
- **FR-011**：用户必须能够在图片内容超出视口时，通过单指平移手势移动图片；平移到内容边缘过界后有阻尼效果，松手后自动回弹到合法范围。
- **FR-012**：用户必须能够通过双指旋转手势旋转图片，旋转时图片实时跟随旋转角度变化；松手后图片以动画方式自动对齐到最近的 90° 倍数位置。
- **FR-013**：系统必须在图片加载过程中展示 loading 状态；loading 状态的 UI 由接入方定义，SDK 通过状态回调通知加载进度。
- **FR-014**：系统必须在图片加载或解码失败时展示 error placeholder；error placeholder 的 UI 完全由接入方定义，SDK 通过错误回调通知失败类型。
- **FR-015**：系统必须在设备内存不足时（onLowMemory 回调）自动释放低优先级 Tile 缓存，必要时降级解码精度，保证查看器不崩溃、不产生 ANR。
- **FR-016**：SDK 必须支持通过配置参数设定 Tile 大小、内存缓存上限、解码线程数；SDK 须提供合理的默认值，使接入方无需强制配置即可正常使��。

### NFR（Non-Functional Requirements）

#### 性能（Performance）

- **NFR-PERF-001**：手势操作（缩放、平移、旋转）期间，渲染帧率须在支持 60fps 的设备上达到 ≥ 60fps，在支持 120fps 的设备上达到 ≥ 120fps。验收方式：使用 Perfetto 或 Android GPU Inspector 录制手势操作 10 秒，统计丢帧率，允许偶发丢帧不超过 1%。
- **NFR-PERF-002**：普通图片（≤ 20MP）从发起加载到首帧可见（不计网络耗时）的时间，在中端设备（如 Snapdragon 778G 级别）上 p95 ≤ 500ms。验收方式：本地文件加载场景下，使用 Benchmark 测试库采集 100 次首帧可见耗时，取 p95。
- **NFR-PERF-003**：超大图（2 亿像素，本地文件）从加载开始到用户可进行手势操控（低分辨率预览可见）的时间，在中端设备上 p95 ≤ 2000ms。验收方式：Benchmark 测试库采集 20 次，取 p95。
- **NFR-PERF-004**：Tile 重解码请求发出后，在 Wi-Fi 或本地文件场景下，目标 Tile 完成高清渲染的时间 p95 ≤ 800ms（中端设备）。验收方式：Benchmark 测试库在 5× 缩放状态下平移触发新 Tile 解码，采集 50 次，取 p95。

#### 功耗（Power）

- **NFR-POWER-001**：图片浏览期间（无手势操作的静止查看状态），SDK 不执行任何后台解码、轮询或定时任务；CPU 使用率应降低至接近 0%（仅 GIF 播放时除外）。验收方式：静止查看静态图片 60 秒，使用 Battery Historian 或 Android Energy Profiler 确认无后台 CPU 唤醒。
- **NFR-POWER-002**：GIF 动图播放期间，帧解码在专用解码线程上执行，不阻塞主线程；CPU 使用率应与图片原始帧率和分辨率成正比，SDK 不引入超出原始播放需求的额外 CPU 开销。验收方式：使用 Profiler 观察 GIF 播放期间线程分布与 CPU 使用率，确认主线程无解码负载。

#### 内存（Memory）

- **NFR-MEM-001**：在 4GB RAM 设备上加载 2 亿像素 JPEG 并进行完整手势操控（1× → 5× → 1×），全程 RSS 内存峰值增量（相对于加载前）不超过 512MB。验收方式：Android Studio Memory Profiler 记录全程堆内存，确认无 OOM 且峰值增量符合约束。（注：具体上限待技术方案确定后可在 plan.md 中细化。）
- **NFR-MEM-002**：关闭查看器后，SDK 持有的所有 Tile 缓存和解码资源须在 30 秒内完全释放（通过 GC 周期），不产生内存泄漏。验收方式：LeakCanary 检测查看器生命周期，确认关闭后无泄漏告警；Profiler 确认堆内存在 30 秒内回落到打开前水平。
- **NFR-MEM-003**：系统触发 onLowMemory 时，SDK 在 500ms 内释放不少于 50% 的 Tile 缓存占用。验收方式：模拟 onLowMemory 事件，使用 Profiler 测量释放耗时与释放量。

#### 安全与隐私（Security/Privacy）

- **NFR-SEC-001**：SDK 不收集、上报或持久化任何用户数据（包括用户浏览的图片内容、URL、操作行为等）；SDK 不申请任何额外 Android 权限，所需存储/网络权限由接入方在宿主应用声明。
- **NFR-SEC-002**：SDK 对接入方提供的图片数据源（URL、文件路径、URI）只执行读取操作，不修改、不复制到 SDK 私有存储目录。
- **NFR-SEC-003**：SDK 不在任何公开日志（Logcat）中输出图片 URL 的完整路径或含敏感信息的字段（如 token 参数）；调试日志须在 Release 构建中默认关闭。

#### 可观测性（Observability）

- **NFR-OBS-001**：SDK 必须通过回调接口向接入方暴露以下状态事件（最低要求）：图片加载开始、加载成功（含图片原始宽高）、加载失败（含错误类型枚举）、Tile 解码失败（含 Tile 坐标与失败原因）。
- **NFR-OBS-002**：SDK 内部关键路径（解码开始/结束、缓存命中/未命中、内存释放触发）须有 Debug 级别日志输出，日志 Tag 统一为 `MediaViewerSDK`，在 Release 构建中默认关闭（可通过配置开启）。
- **NFR-OBS-003**：SDK 必须提供解码耗时的性能数据回调（可选订阅），包含：Tile 解码耗时（ms）、当前缓存命中率、当前内存占用（MB），供接入方接入自有 APM 系统。

#### 可靠性（Reliability）

- **NFR-REL-001**：快速连续切换图片 100 次（与 FEAT-002 集成后验证），不发生崩溃，内存无持续增长（每轮切换后内存须回落到合理水位）。
- **NFR-REL-002**：在内存���张场景下（onLowMemory），SDK 不产生 ANR（主线程不阻塞超过 5 秒），不崩溃。
- **NFR-REL-003**：SDK 对图片解码失败（任意原因）的处理路径须有单元测试覆盖，确保失败路径不引发未捕获异常。

## 验收标准（Feature Level）

- **AC-001**（→ FR-001）：将一张标准 JPEG 图片文件路径传入 SDK，图片正确解码并在查看器中完整清晰地渲染，无色彩偏差，无截断。
- **AC-002**（→ FR-002）：将一张含 Alpha 透明通道的 PNG 图片传入 SDK，图片正确解码并渲染，透明区域正确显示为透明（不填充黑色或白色）。
- **AC-003**（→ FR-003）：在 Android 9.0 及以上设备上，将一张 HEIC 图片传入 SDK，图片正确解码并渲染；在 Android 8.0 设备上，SDK 不崩溃，展示 error placeholder 或降级结果。
- **AC-004**（→ FR-004）：将一张静态 WebP 和一张动态 WebP 分别传入 SDK，两者均正确解码并渲染；动态 WebP 按帧播放。
- **AC-005**（→ FR-005）：将一张 BMP 图片传入 SDK，图片正确解码并渲染。
- **AC-006**（→ FR-006）：将一张 GIF 动图传入 SDK，图片进入视口后按原始帧率自动播放（通过帧计数器或录屏验证帧率）；图片完全离开视口后停止播放。
- **AC-007**（→ FR-007 + NFR-MEM-001）：在 4GB RAM 设备上加载 2 亿像素 JPEG 本地文件，完成 1× → 5× → 1× 完整操控，全程不发生 OOM，RSS 内存峰值增量 ≤ 512MB。
- **AC-008**（→ FR-008）：图片放大至 5× 后，当前视口范围内的 Tile 区域重新以高清精度解码，通过像素对比确认无明显模糊（主观评测：无肉眼可见的方块化或模糊感）。
- **AC-009**（→ FR-007）：在 5× 放大状态下，仅当前视口所在 Tile 处于解码或已解码状态；通过日志验证视口外 Tile 未被触发解码。
- **AC-010**（→ FR-009）：图片处于 1× 状态时双击，图片放大到 2×，以点击位置为中心；再次双击图片回到 1×；图片处于 5× 时双击，倍率不变。
- **AC-011**（→ FR-010）：捏合放大，当倍率超过 5× 时有橡皮筋阻尼，松手后图片回弹到 5×；倍率始终不超过 5× + 阻尼允许的临时区间（阻尼区间由实现定义，不超过 5× 的 20%）。
- **AC-012**（→ FR-010）：捏合缩小到 1× 以下有阻尼，松手后回弹到 fit-screen（1×）；倍率始终不低于 1× - 阻尼允许的临时区间。
- **AC-013**（→ FR-008）：在任意缩放倍率（1×、2×、3×、5×）下平移到新区域，对应区域 Tile 以当前倍率对应精度重新解码，无拉伸模糊。
- **AC-036**（→ FR-011）：图片内容超出视口（任意方向），可通过单指平移移动图片；图片内容未超出视口时，平移手势不响应。
- **AC-037**（→ FR-011）：平移到内容边缘过界后松手，图片回弹到合法范围（内容边缘不超出视口对应边）。
- **AC-038**（→ FR-012）：双指旋转时，图片实时跟随旋转角度变化，无明显延迟（延迟 < 1 帧）。
- **AC-071**（→ FR-012）：旋转松手后，图片以可见动画（时长 100ms ~ 300ms）对齐到最近的 90° 倍数，动画结束后图片恰好处于 0°/90°/180°/270° 之一。

## 核心实体

- **图片数据源（ImageSource）**：表示一张图片的来源描述，核心属性包括：数据源类型（网络 URL / 本地文件路径 / ContentResolver URI）、MIME 类型（可选，用于辅助格式判断）。与图片浏览器（ImageViewer）是一对一关系；由接入方在使用时提供，SDK 不持久化该信息。
- **Tile（分块）**：超大图被切分后的一个矩形区域单元，核心属性包括：在原始图坐标系中的位置与尺寸、所属的解码精度等级（对应缩放倍率区间）、当前解码状态（未解码 / 解码中 / 已解码 / 已释放）。Tile 的数量与大小由 SDK 根据图片尺寸和配置参数动态计算。Tile 之间相互独立，按需解码与释放。
- **视口（Viewport）**：查看器当前可见的屏幕区域在图片坐标系中的映射矩形，核心属性包括：中心点坐标、可见宽高、当前缩放倍率、当前旋转角度。视口随手势操作实时变化，驱动 Tile 调度决策（哪些 Tile 需要解码、哪些可以释放）。
- **缩放状态（ZoomState）**：描述图片当前的变换信息，核心属性包括：缩放倍率（scale）、旋转角度（rotation，对齐后为 90° 倍数）、平移偏移（offsetX, offsetY）。缩放状态是手势交互的中间产物，也是渲染层的输入。

## 假设与约束

- **假设**：
  - 假设接入方注入的图片加载框架能够正确处理网络请求、缓存和数据返回，SDK 不对加载框架内部行为负责；若加载框架行为异常导致 SDK 未收到有效数据，SDK 维持 loading/error 状态。
  - 假设 Android 系统的区域解码能力在目标设备上可用；若不可用（厂商定制裁剪），SDK 降级为全图采样解码，不保证超大图的内存约束，但保证不崩溃。
  - 假设接入方正确实现了 error placeholder 和 loading UI；SDK 不提供默认样式，若接入方未实现则相关状态无视觉反馈（SDK 不崩溃）。
- **约束**：
  - 最低支持 Android 8.0（API 26）；HEIF/HEIC 硬件解码仅支持 Android 9.0（API 28）及以上。
  - SDK 使用 Kotlin 编写，要求接入方项目使用 Kotlin 或 Java（Java 互操作性须保证）。
  - SDK 不依赖任何第三方图形库（如 Glide、Coil），图片加载框架由接入方注入。
  - 单张图片最大支持 2 亿像素；超过此限制的图片行为未定义（可在 plan.md 中决策是否添加超限判断与提示）。
  - SDK 不支持 PDF、TIFF、Camera RAW 等格式（不在本 EPIC 范围内）。
