# 需求工程（评审 + 规格书）

统一处理「原始需求材料 → 可评审、可设计、可开发、可测试」的完整链路。

## 工作模式

根据用户意图自动选择模式；未明确时默认 `full`。

| 模式 | 触发词示例 | 产出 |
|------|-----------|------|
| `review` | 评审 PRD、找问题、待确认项、需求风险 | 问题清单 |
| `spec` | 转成规格书、生成 spec/SRS | 需求规格书 |
| `full` | 完整处理、先审后写、转 spec（默认） | 评审 + 规格书 |

用户指定 `--review` / `--spec` / `--full` 或「只要评审」「只要规格书」时，按指定模式执行。

## 核心原则

**评审模式**
- 核心是**问题清单**，不是功能拆解或方案设计
- 尽量引用 PRD 原文；推断须标注「基于推断，非 PRD 明确说明」
- 不擅自补全产品意图并当成确定事实

**规格书模式**
- 输出的是**需求规格书**，不是对 PRD 的简单复述
- 优先保留明确事实，禁止编造业务规则、指标或边界条件
- 区分：`✅ 已明确` / `⚠️ 合理推断` / `❓ 待确认`
- 每条功能需求须可理解、可验证、可追踪

**full 模式**
- 先完成评审，再将高/中优问题映射到规格书的 `O-001` 待确认项
- 评审结论写入规格书「约束、风险与待确认事项」章节

## 输入形式

- 产品需求文字描述
- 原始或非标准 PRD 文本
- PRD 文档链接（Confluence、Notion、飞书、网页）

### 输入处理

**文档链接**：先用 `WebFetch` 抓取；无法访问则要求用户粘贴正文或导出文档。

**文字描述**：直接解析；明显不完整时指出「分析结论会受限」。

## 统一流程

### 阶段 1：获取与归一化

从原始材料提取并统一术语：

- 背景、目标、范围、不做什么
- 用户角色、权限、典型场景
- 功能点、操作流程、异常流程、边界情况
- 业务规则、状态变化、约束条件
- 数据项、输入输出、外部依赖
- 非功能要求、验收口径

术语前后一致；统一使用「需求规格书 / 规格书」，不混用「方案文档」「说明书」。

### 阶段 2：缺口审查

识别：信息缺失、表达歧义、前后冲突、不可验证项。

**阻塞级缺口**（须先向用户提问，不能直接定稿）：
- 核心目标用户不明
- 做什么 / 不做什么不明
- 主流程无法确定
- 关键规则互相冲突
- P0 功能无可验收结果
- 外部依赖直接影响方案成立

**非阻塞缺口**：可先输出并标记 `❓ 待确认`（次要边界、指标口径、文案埋点等）。

## 分支 A：评审输出（review / full 第一步）

### 审查步骤

1. 用 3–5 句话建立审查上下文（目标、用户、核心动作、影响范围、成功标准）
2. 按 [review-dimensions.md](review-dimensions.md) 十个维度逐项扫描
3. 问题归类、按优先级排序（高 → 中 → 低）
4. 使用 [review-template.md](review-template.md) 生成文档

### 输出位置

- `docs/requirements/[功能中文名]-PRD评审.md`

用户要精简版时，用 review-template 中的精简模板。

---

## 分支 B：规格书输出（spec / full 第二步）

### 最小信息清单

尽量确认：业务背景与目标、目标用户、范围边界、关键场景、核心功能、业务规则、数据 I/O、非功能要求、外部依赖、验收标准。

### 写作要求

- 章节结构见 [reference.md](reference.md)
- 功能需求 `FR-001`、非功能 `NFR-001`、验收 `AC-001`、风险 `R-001`、待确认 `O-001`
- 先总后分，先范围后细节；用表格呈现需求、规则、依赖、风险
- 每条功能需求含：触发者、触发动作、系统行为、结果输出、限制/异常

### full 模式衔接

- 评审中的 `Q-xxx` 高/中优问题 → 规格书 `O-001` 系列
- 规格书「8. 信息来源说明」引用评审中的显式/推断区分

### 输出位置

- `docs/requirements/[功能中文名]-需求规格.md`

用户指定路径时遵循用户要求。

### 输出前质量校验

- [ ] 每个核心功能可单独验收
- [ ] 覆盖主路径、异常路径、边界路径
- [ ] 已明确范围与非范围
- [ ] 非功能需求至少可验证
- [ ] 未混入实现细节、技术方案或数据库设计

---

## 重要边界

- 不把实现方案、类图、数据库表设计当成需求规格书主体
- 不把「可能的技术实现」写成「已确认需求」
- 不因原始 PRD 混乱就照抄结构，必须重组为标准结构
- 用户要求技术方案 / 架构设计时，改用其他 design skill
