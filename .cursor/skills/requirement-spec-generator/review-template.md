# PRD 评审输出模板

## 完整版

```markdown
# [功能名称] PRD 评审

> 分析时间：YYYY-MM-DD
> 需求来源：[PRD 链接 / 口述整理 / 原始文本]

## 1. 需求概览

- 目标一句话总结：[简述该需求想解决什么问题]
- 影响范围：[页面 / 模块 / 角色]
- 当前判断：[需求可理解程度，高 / 中 / 低]
- 是否建议进入开发：[可以 / 不建议 / 需先确认高优问题]

---

## 2. 关键问题清单

| 编号 | 类型 | 优先级 | 原文/依据 | 问题描述 | 为什么是问题 | 影响范围 | 需产品明确内容 | 建议追问 |
|------|------|--------|-----------|----------|----------------|----------|------------------|----------|
| Q-001 | 信息缺失 | 高 | [引用原文或写「PRD 未提及」] | [缺了什么] | [为什么缺失会阻塞] | [影响设计/开发/测试/上线] | [需要补充什么] | [建议怎么问产品] |
| Q-002 | 描述模糊 | 高 | "[原文]" | [哪里模糊] | [可能有几种理解] | [会导致什么分歧] | [要明确哪个口径] | [建议问题] |
| Q-003 | 逻辑冲突 | 中 | "[原文 A]" + "[原文 B]" | [冲突点] | [为什么矛盾] | [会影响什么] | [以哪个规则为准] | [建议问题] |

---

## 3. 按类别汇总

### 3.1 高优先级问题

- [Q-001] [一句话概述]
- [Q-002] [一句话概述]

### 3.2 中优先级问题

- [Q-00X] [一句话概述]

### 3.3 低优先级问题

- [Q-00X] [一句话概述]

---

## 4. 缺失主题检查

若 PRD 完全未覆盖但通常必须明确，可列出：

- 角色与权限：[是否缺失]
- 数据定义：[是否缺失]
- 状态与异常处理：[是否缺失]
- 验收标准：[是否缺失]
- 外部依赖：[是否缺失]

---

## 5. 建议与下一步

- 建议先与产品确认的 Top 3 问题：
  1. [问题 1]
  2. [问题 2]
  3. [问题 3]

- 建议补充到 PRD 的内容：
  [列出建议补充的章节或字段]

---

## 6. 说明

- 显式信息：[来自原文的明确表述]
- 推断信息：[基于上下文的推断，需单独标注]
- 本文目标：帮助产品补全文档、帮助研发减少返工，不代表最终方案设计
```

## 精简版

用户只要简短结论时使用：

```markdown
# [功能名称] PRD 问题清单（精简版）

## 结论
- 当前 PRD 主要问题数：[X]
- 高优先级问题数：[X]
- 当前是否足够进入开发：[可以 / 不建议]

## 待确认问题
1. [高] [问题]
2. [高] [问题]
3. [中] [问题]
4. [中] [问题]
5. [低] [问题]

## 建议
- 建议产品先补充：[最关键缺失项]
```

## 问题类型

- `信息缺失`：开发必须知道，但 PRD 没写
- `描述模糊`：写了，但表述不明确
- `存在歧义`：同一句话可能有多种理解
- `逻辑冲突`：前后描述不一致或规则相互打架
- `边界遗漏`：极端 / 异常 / 取消 / 回退等场景没写
- `角色权限不清`：谁能做、谁不能做没有说清
- `数据口径不清`：字段、来源、单位、计算口径不明确
- `验收缺失`：无法判断需求是否完成
- `依赖待确认`：依赖外部条件但未明确
- `风险项`：即使 PRD 写了，但落地风险高，需要提前确认

## 优先级

- `高`：不确认就无法设计、开发、测试或会导致方向错误
- `中`：可以继续推进，但后续大概率返工
- `低`：不影响主链路，可在详细设计或联调前确认

排序原则：先排阻塞开发 → 再排导致返工 → 最后排体验细节。

## 质量检查

- [ ] 是否以「问题清单」为核心而不是功能列表
- [ ] 是否覆盖缺失、模糊、歧义、冲突、边界、异常、验收、依赖
- [ ] 是否标注原文依据或明确说明「PRD 未提及」
- [ ] 是否给出了优先级、影响范围和建议追问
- [ ] 推断类问题是否标注「基于推断」
