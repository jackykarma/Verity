# 业务功能文档套件生成器

为一个业务/模块**成体系地**生成一整套技术文档。与单篇文档不同，本 skill 的核心价值是：**先拆解、再分治**——用功能树把大模块切成可独立成文的小单元，从而避免单个文档过长、难维护、难评审。

产出的「文档套件」由四部分组成，每部分都有配套的标准模板：

| # | 文档部分 | 模板文件 | 面向 |
|---|----------|----------|------|
| 1 | **功能树**（拆解索引） | 见下文「功能树模板」 | 全员，作为套件导航 |
| 2 | **业务功能技术实现文档** | `references/feature-tech-doc-template.md` | 工程师 |
| 3 | **技术框架文档**（整体架构 + 框架模块详细设计） | `references/framework-design-template.md` | 工程师/架构评审 |
| 4 | **API 接口文档**（依赖的后端 REST + 对外提供的代码接口） | `references/api-doc-template.md` | 工程师/联调对接 |

> 模板文件较大，**用到哪部分再读哪个 reference**，不必一次性全部加载。

---

## 适用场景

- 一个大模块/业务线需要从零补齐成体系的技术文档，而不是零散单篇
- 已有文档单个文件过大、难以维护，需要按功能树拆分重组
- 新人入职需要一套可导航、由浅入深的文档集
- 架构评审、技术交接前需要框架设计 + 业务实现 + 接口契约的完整资料
- 套件已存在，代码发生变更或新增功能后，需要**增量更新**受影响的文档

### 与相邻 skill 的边界

| 用户诉求 | 应使用 |
|----------|--------|
| 功能树 / 业务功能技术实现 / 技术框架设计 / API 接口文档（含单篇或成套） | **本 skill**（可按阶段只产出其中一部分，如仅功能树或仅某功能的技术实现） |
| 场景文档（前提/操作/预期） | `feature-scenario-doc` |

## 产出物：文档套件目录结构

所有文档落到 **`docs/project/[模块中文名]/`** 下，按四部分分目录组织（文件名均为简体中文）：

```
docs/project/[模块中文名]/
├── 文档总览.md                      ← 套件入口：简介 + 功能树导航 + 各文档索引
├── 功能树.md                        ← 第1部分：树形拆解（决定其余文档如何切分）
├── 技术框架/
│   ├── 架构设计.md                  ← 整体架构（分层/选型/跨切面/ADR）
│   ├── 网络框架详细设计.md          ← 各技术框架模块（按工程实际命名）
│   ├── 本地存储框架详细设计.md
│   └── ...详细设计.md
├── 业务功能/
│   ├── [功能A]/
│   │   ├── 功能概览.md              （仅多子功能时）
│   │   ├── 技术实现-[子功能1].md
│   │   └── 技术实现-[子功能2].md
│   └── [功能B]/
│       └── 技术实现.md              （单一功能直接一篇）
└── 接口文档/
    ├── 依赖后端接口.md              ← 依赖的外部 REST/HTTP API
    └── 对外提供接口.md              ← 本模块暴露的代码接口/SDK
```

> 无 `docs/project/` 工程上下文时，可与用户确认改用其它目录，或在对话中直接产出。

## 核心原则：拆解优先，避免巨型文件

1. **先树后文**：永远先产出功能树，再据此切分业务功能文档。功能树是套件的"目录骨架"，决定了哪些功能各自成文、哪些合并。
2. **单文件单主题**：一篇文档只讲一个功能/一个框架模块/一个业务域的接口。一篇超过几百行就应考虑按功能树进一步拆分。
3. **横向分类，纵向分层**：横向分四类（功能树/业务功能/技术框架/接口），每类纵向再按树拆细。
4. **基于事实，而非臆测**：所有内容来源于真实代码、配置、注释、已提供上下文；不得凭经验"补全业务"。区分 ✅ 已确认 / ⚠️ 合理推断（须说明依据）。
5. **真实命名**：所有类图、时序图、流程图的类名/participant 必须是工程真实类名，禁止套用 Clean Architecture 等示例分层凭空编造（详见 `.cursor/rules/specify-diagram-requirements.mdc`）。
6. **新人优先**：默认读者是第一次接触该模块的工程师，不留隐含知识。

## 工作流程

### 阶段 0：范围确认与信源识别

先检查 `docs/project/[模块中文名]/` 是否已存在套件：**已存在则进入「增量更新模式」（见下文），不要全量重写**。

向用户确认（若未明确）：
1. **套件根对象**：是整个产品/业务线，还是某个模块/功能？据此确定 `[模块中文名]`。
2. **本次产出范围**：四部分全做，还是先做其中几部分？（可分批迭代，先树→框架→业务→接口）
3. **信源模式**：
   - 有 `epic.md`/`spec.md`/PRD → **文档驱动**
   - 仅有代码 → **代码逆向**（读码顺序：导航/入口 → ViewModel/Presenter → UseCase/Domain → Repository/框架层）
   - 口述 → **口述构建**
   - 混合 → 优先文档，代码补充，口述补全

### 阶段 1：功能树拆解（必做，且最先做）

按下文「功能树模板」产出 `功能树.md`：
- 业务级根节点（模块）→ 一级功能 → 二级子功能 →（必要时）三级操作项，建议 ≤ 4 层。
- 节点用**产品语言**命名，不用代码类名。
- 同时识别**技术框架候选**：在拆解过程中，把"被多个功能复用的技术底座"（网络、存储、DI、图片加载、线程、基础架构等）单独记下，作为技术框架文档的清单来源。
- 功能树同时充当后续文档的**切分依据**：每个一级功能（或其下子功能）对应「业务功能」目录里的一篇文档。

### 阶段 2：技术框架文档

读 `references/framework-design-template.md`，产出：
- **一篇 `架构设计.md`**（模板 A）：整体分层、模块边界、技术选型、跨切面机制、ADR、框架模块清单。
- **每个技术框架模块一篇 `[模块名]详细设计.md`**（模板 B）：定位、类图、核心机制时序图、扩展点、接入方式、配置、错误处理。
- 框架模块清单来自阶段 1 识别出的技术底座，按工程真实模块命名。

### 阶段 3：业务功能技术实现文档

读 `references/feature-tech-doc-template.md`，**按功能树逐个功能**产出：
- 单一功能 → 一篇 `技术实现.md`。
- 多子功能 → 一篇 `功能概览.md` + 每个子功能一篇 `技术实现-[子功能].md`。
- 每篇必须含全部章节，且类图含全部关键类与接口、时序图完整覆盖调用链并紧跟「协作者与过程说明」、流程图覆盖正常+异常（详见模板与 `.cursor/rules/specify-diagram-requirements.mdc`）。

### 阶段 4：API 接口文档

读 `references/api-doc-template.md`，产出：
- **依赖的后端 REST API** → `依赖后端接口.md`（模板 A）：请求/响应/字段/错误码/对应客户端模型。
- **对外提供的代码接口** → `对外提供接口.md`（模板 B）：公共类/接口、方法签名、回调契约、使用示例、错误码。
- 二者按需选用；接口多时按业务域拆多篇，避免单文件过大。

### 阶段 5：生成文档总览（索引）

按下文「文档总览模板」产出 `文档总览.md`，作为套件入口与进度看板。

## 增量更新模式（套件已存在时）

套件是"活文档"，多数时候执行的是更新而非重建。流程：

1. **定位变更**：从用户描述 / git diff / 代码对比确定本次变更涉及哪些功能节点或框架模块。
2. **查切分映射**：通过 `功能树.md` 的「文档切分映射」「技术框架候选清单」找到受影响的文档清单。
3. **最小化更新**：
   - 新增功能 → 功能树加节点 + 新增对应技术实现文档
   - 功能内部实现变化 → 只更新对应 `技术实现-*.md` 的相关章节与图表
   - 框架变化 → 更新对应 `*详细设计.md`；若影响分层/选型，同步 `架构设计.md`
   - 接口变化 → 更新接口文档对应条目（新增/废弃须更新总览表与兼容性说明）
4. **同步索引**：凡增删文档或节点，必须同步刷新 `功能树.md` 的映射表与 `文档总览.md` 的索引和进度。
5. **更新元信息**：被改动文档的「版本/更新日期」须递增，便于读者判断新鲜度。

**禁止**：因局部变更而全量重写整个套件；只改正文不改 `文档总览.md`/`功能树.md` 索引（会导致导航失真）。

## 执行节奏与互链规范

一个中等模块的套件往往有 10+ 篇文档，一次性全部生成容易上下文溢出、后半程质量滑坡。因此：

- **逐篇落盘**：每写完一篇立即写入文件，不要在内存里攒一批再写。
- **分阶段确认**：每完成一个阶段（树/框架/业务/接口），向用户简报已产出清单与下一步，规模大时让用户决定是否继续或调整优先级。
- **质量恒定**：写到后面的文档必须与第一篇同等详尽；发现上下文不足时，停下来重新读相关代码，而不是靠记忆泛写。

**互链规范**（让套件可导航的关键）：
- 所有跨文档引用使用**相对路径** Markdown 链接，如 `../技术框架/网络框架详细设计.md`。
- 业务功能文档中涉及框架机制 → 链接到对应框架详细设计；涉及接口契约 → 链接到接口文档。
- 每篇文档的「相关文档」或「阅读前提」中至少回链 `文档总览.md`。

## 实施规范

### 必须事项

- **先产出功能树**，再据此切分其余文档；功能树是套件的骨架。
- 所有文档落到 `docs/project/[模块中文名]/` 对应子目录，**文件名均为简体中文**。
- 产出 `文档总览.md` 作为套件入口与进度索引。
- 单一功能用 `技术实现.md`；多子功能用 `功能概览.md` + 多篇 `技术实现-[子功能].md`。
- 每个技术框架模块单独成篇详细设计；整体架构单独成篇 `架构设计.md`。
- 图表 participant/类名为真实类名；时序图紧跟「协作者与过程说明」；图表覆盖正常 + 异常。
- 区分 ✅ 已确认 / ⚠️ 合理推断，推断须说明依据。
- 跨文档引用使用相对路径链接；每篇文档至少回链 `文档总览.md`。
- 套件已存在时走增量更新；增删文档/节点必须同步刷新 `功能树.md` 映射与 `文档总览.md` 索引。
- 逐篇落盘，分阶段向用户简报进度。

### 禁止事项

- 把所有内容堆进一个巨型文件（违背本 skill 的核心目的）。
- 跳过功能树直接写业务文档。
- 用代码类名作为功能树节点名。
- 类图/时序图使用虚构或示例类名；套用 Clean Architecture 等模板分层凭空编造。
- 时序图用「...」省略关键调用，或缺少「协作者与过程说明」。
- 只写 Happy Path，忽略异常/降级/错误处理。
- 把 `implementation project(':xxx')` 当作依赖 SDK 列出。
- 同一机制在业务功能文档与框架文档中重复成文（业务文档应链接框架文档，而非复制）。
- 套件已存在时全量重写，或更新正文却不同步索引。
