# Feature Documentation Generator

为项目中的业务功能自动生成结构化文档，包含业务视角和技术实现两个层面。

## 文档认知模型

### 多子功能时的文档拆分原则

- **若功能包含多个子功能**：用一篇 **overview** 文档整体介绍，再用多篇文档分别详细介绍每一个子功能。
- **若功能为单一功能**：可直接写一篇技术文档，无需单独的 overview。

```
Feature（业务功能）
 ├─ 概览文档（仅当存在多个子功能时）
 │   └─ overview.md — 功能整体介绍、子功能列表、整体架构与关系
 │
 ├─ 技术实现文档（给工程师，每篇必须包含下列全部内容）
 │   ├─ 文档元信息（目的、读者、前提、版本）
 │   ├─ 功能介绍（含范围与边界）
 │   ├─ 领域概念（术语表）
 │   ├─ 整体架构（多层架构图 + 分层/数据流/设计决策）
 │   ├─ 关键模块设计与实现要点（含模块调用链概览）
 │   ├─ 类图（必须包含所有关键类与接口，含 interface，基于真实代码）
 │   ├─ 时序图（多张，每张须完整覆盖调用链与所有关键方法调用，含正常+异常流程）
 │   ├─ 流程图（多张，每张须覆盖所有分支节点，含正常+异常流程，与时序图一致）
 │   ├─ 关键数据结构
 │   ├─ 数据库、数据表设计（表字段、字段含义、字段数据类型）
 │   ├─ 依赖的 SDK 与配置（名称、groupId、artifactId，不含 implement project；含配置项与开关）
 │   ├─ 对外提供的接口
 │   ├─ 错误码与异常处理（含触发场景）
 │   ├─ 日志、埋点与常见问题（结构化日志表 + 埋点事件表）
 │   └─ 附录（缩写对照表、相关文档、信息来源说明）
 │
 └─ 场景地图文档（一篇）
     └─ scenario-map.md — 功能 → 子功能 → 场景表格（前提、操作、预期结果与表现）
```

## 适用场景

- 新功能上线，需要补齐项目文档
- 新人入职，需要快速理解某个业务模块
- 存量系统缺乏结构化文档
- 代码 Review / 架构演进前做系统梳理

## 核心原则

### 1. 基于事实，而非臆测

所有内容必须来源于：
- 代码结构
- 命名
- 注释
- 配置
- 已提供上下文

**不得凭经验"补全业务"**

### 2. 明确区分信息确定性

使用以下标记：
- ✅ **已确认信息**（From Code / Config）
- ⚠️ **合理推断**（Inference Based on Code）

### 3. 新人优先（New Joiner First）

默认读者：第一次接触该模块的工程师

禁止：
- 只给结论不给背景
- 技术文档中仅用类名代替概念说明而不加解释

## 使用流程

### 步骤 1：理解需求

当用户请求"创建XX功能的文档"时：

1. 确认功能范围：明确用户指的是哪个模块/包/功能

### 步骤 2：代码探索

按照认知模型的层次结构收集信息；**先判断该功能是否包含多个子功能**（按包/模块/用例边界划分），以决定是否生成 overview 及多篇 technical。

#### 2.1 架构全景探索

1. **识别代码边界与子功能**：
   - 使用 Glob 找到相关的代码文件
   - 使用 SemanticSearch 理解："XX功能涉及哪些模块？是否有可拆分的子功能？"
   - 识别外部依赖（数据库、API、第三方库，用于「依赖的 SDK」章节，且排除 project 依赖）

2. **绘制模块全景**：
   - 识别所有关键类和接口
   - 理解模块间的依赖关系
   - 确定数据流方向

#### 2.2 端到端流程探索

1. **主流程识别**：
   - 使用 SemanticSearch："XX功能的主流程是什么？"
   - 追踪从用户操作到系统响应的完整路径
   - 识别关键步骤和决策点

2. **异常流程识别**：
   - 查找 try-catch、错误处理代码
   - 识别降级策略和容错机制
   - 理解失败场景的处理方式

#### 2.3 模块拆解探索

1. **分析关键模块**：
   - 阅读核心类、接口、方法
   - 理解每个模块的职责边界
   - 识别模块的输入输出

2. **深入模块细节**：
   - 核心数据结构和状态管理
   - 对外接口和协议定义
   - 关键算法和策略实现

#### 2.4 业务概念提取

1. **提取业务概念（用于「领域概念」章节）**：
   - 从类名、方法名提取业务术语，列出名称与含义
   - 阅读注释理解业务规则
   - 识别状态机、流程节点

2. **收集配置信息（用于「依赖的 SDK 与配置」章节）**：
   - 查找配置文件、常量定义
   - 查找 Feature Flag、环境变量等开关配置
   - 查找业务规则的硬编码部分

#### 2.5 错误处理与日志探索

1. **错误码与异常（用于「错误码与异常处理」章节）**：
   - 查找自定义异常类、错误码枚举/常量
   - 识别每种异常的触发场景与处理方式
   - 查找 try-catch 的捕获逻辑与降级策略

2. **日志与埋点（用于「日志、埋点与常见问题」章节）**：
   - 查找 Log.d/e/w、Timber、自定义日志工具的 Tag 与关键输出内容
   - 查找埋点事件名称、触发时机、关键参数
   - 识别排查问题时最有价值的日志节点

### 步骤 3：生成文档

根据[文档模板](#文档模板)生成相应文档。

- **多子功能**：生成 overview.md、technical-[子功能名].md（每子功能一篇）、scenario-map.md
- **单一功能**：生成 technical.md、scenario-map.md
- **技术文档**：每篇必须包含全部必含章节（见文档认知模型）；
  - 类图须包含**所有**关键类与接口（含 interface），禁止虚构类名；
  - 时序图须完整覆盖从触发点到响应的调用链，**所有关键方法调用逐一体现**，不得用「...」代替，每张含正常 + 异常流程；
  - 流程图须覆盖所有关键判断节点与分支，不得遗漏，每张含正常 + 异常流程，与时序图保持一致；
  - 模板文件：`docs/template/technical-doc-template.md`
- 对于不确定的信息，使用 ⚠️ 标记并说明推断依据

### 步骤 4：输出文件

将生成的文档保存到项目中的 **`docs/project/features/`** 目录，创建以 **feature 名称命名的子目录**，并在其下存放所有文档：

```
docs/
└── project/
    └── features/
        └── [feature-name]/           # 以功能名称命名的目录
            ├── overview.md            # 仅多子功能时：功能整体概览
            ├── technical.md          # 单一功能时的技术文档
            ├── technical-[子功能A].md # 多子功能时：子功能 A 技术文档
            ├── technical-[子功能B].md # 多子功能时：子功能 B 技术文档
            └── scenario-map.md        # 场景地图（前提、操作、预期结果）
```

- **单一功能**：`overview.md` 可不生成；仅生成一篇 `technical.md`。
- **多子功能**：必须生成 `overview.md`，并为每个子功能生成一篇 `technical-[子功能名].md`。
- **场景地图**：始终生成一篇 `scenario-map.md`。

## 实施规范

### 禁止事项

**技术文档中禁止**：
- 遗漏必含章节（文档元信息、功能介绍含范围与边界、领域概念、整体架构、关键模块设计含调用链、类图、时序图、流程图、关键数据结构、数据库设计、依赖 SDK 与配置、对外接口、错误码与异常处理、日志埋点与常见问题、附录）
- 类图遗漏关键类或接口（**必须包含所有关键类与接口，含 interface**）
- 时序图不完整：遗漏参与类/接口、关键方法调用，或用「...」代替具体方法调用（**必须逐一体现所有关键方法，调用顺序与代码一致**）
- 流程图不完整：遗漏关键判断节点或分支，或用「...」代替具体分支条件
- 时序图或流程图缺少异常分支（**每张图必须用 alt/else 覆盖正常 + 异常路径**）
- 流程图与时序图的流程节点/分支相互矛盾
- 类图、时序图使用虚构/伪造类名或编造方法调用（须严格基于项目真实代码）
- 将 `implementation project(':xxx')` 列为依赖 SDK
- 只写 Happy Path，忽略异常、降级、错误处理流程

### 必须事项

**必须做到**：
- 存储目录固定为 **`docs/project/features/[feature-name]/`**，以 feature 名称建子目录
- 多子功能时：生成 **overview.md** + 每子功能一篇 **technical-[子功能名].md**
- 每篇技术文档**必须**包含全部章节（见文档认知模型章节列表）
- 类图：包含**所有**关键类与接口（含 interface），基于真实代码，含方法签名与职责说明
- 时序图：**完整覆盖从触发点到响应的调用链**，所有关键方法逐一体现，与代码完全一致；每张含正常 + 异常流程（alt/else）
- 流程图：**覆盖所有关键判断节点与分支**，每张含正常 + 异常流程，与对应时序图保持一致
- 始终生成一篇 **scenario-map.md**，场景三要素：前提、操作、预期结果与表现
- 所有业务规则必须有代码依据；不确定的内容必须标注 ⚠️ 并说明推断依据

## 附加说明

### 生成类图、时序图、流程图

- 须遵循 **`.cursor/rules/mermaid-style-guide.mdc`**（样式配色）。
- **类图**：必须包含**所有**关键类与接口（含 `<<interface>>`），基于项目真实代码，含方法签名与依赖方向；禁止虚构类名。
- **时序图**：必须**完整覆盖从触发点到响应的调用链**，所有关键方法调用逐一体现，方法名与调用顺序与代码完全一致，**不得用「...」代替**；participant 须为真实类/接口名，禁止伪造；每张图须用 alt/else 覆盖正常 + 关键异常路径。
- **流程图**：多张，每张描述一段业务逻辑；**必须覆盖所有关键判断节点与分支，不得用「...」代替**；每张须同时包含正常 + 异常分支；与对应时序图流程节点保持一致，不得矛盾。

### 多子功能时的拆分

- 先写 **overview.md** 整体介绍及子功能列表与关系。
- 每个子功能单独一篇 **technical-[子功能名].md**，每篇都包含技术文档模板中的全部 10 项内容。
- **scenario-map.md** 按子功能分节，每节下用表格列出场景（前提、操作、预期结果与表现）。

### 存储目录

- 根目录：**`docs/project/features/`**
- 每个 feature 一个子目录：**`docs/project/features/[feature-name]/`**
- 该目录下存放：overview.md（可选）、technical*.md、scenario-map.md

### 增量更新

如果文档已存在：
- 读取现有文档
- 对比代码变化
- 增量更新对应章节
- 在文档顶部添加更新日志
