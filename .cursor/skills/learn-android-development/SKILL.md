# Android 开发学习

围绕一个明确主题，输出适合学习的 Android 知识文档或学习包，而不是泛泛的百科介绍。

---

## 学习方法

始终遵循以下方法：

1. 先激活已有认知，再建立新的认知地图，最后进入实现细节。
2. 先回答"为什么会有这个东西"，再解释"它现在怎么工作"。
3. 用用户自己提出的问题驱动学习，内容围绕这些问题展开，而不是通用模板。
4. 用费曼式表达检验理解——能说清楚才算真懂，说不清楚的地方就是要补的漏洞。
5. 用主动回忆（不看文档先尝试复述）和生成效应（先猜后看）固化记忆。
6. 用间隔复习对抗遗忘曲线，学完不代表记住。
7. 深入模式采用"总览 -> 分层 -> 流程 -> 代码 -> 调试"的递进结构。

## 问题前置：学习前先提问（子主题级必做）

**这是最重要的一步，不可省略。**

当用户明确了要学的子主题（如 `Binder`、`View 绘制`、`Choreographer`）时，在生成任何学习内容之前，必须先进入"问题前置"环节。

### 问题前置的目的

- 激活用户已有的认知，避免从零灌输用户已知的内容
- 让用户的好奇心和困惑点成为学习内容的组织主线
- 为后续"验收"提供基准：学完后回头看，哪些问题答了、哪些还没答

### 如何提问

围绕主题，从以下维度主动向用户提问，问题数量不设上限，覆盖所有对学习有价值的角度：

**1. 已有认知探底**
- 你对这���主题目前了解多少？（哪怕一两句话也行）
- 你有没有用过它？遇到过什么问题或困惑？
- 你能描述一下它大概是做什么用的吗？

**2. 问题与困惑收集**
- 你最想搞清楚的是什么？
- 有哪些概念让你觉得很模糊、说不清楚？
- 有没有你见过但没看懂的代码、日志或报错？
- 有没有让你觉得"这两个东西到底有什么区别"的疑问？

**3. 学习目标锚定**
- 学完这个主题，你希望自己能做到什么？（能解释给别人听？能排查问题？能写出来？）
- 你是为了实际项目里遇到的问题来学，还是想系统补知识？
- 学完后你打算做什么实验或验证？

**4. 场景与背景锚定**
- 你当前在做什么项目或功能？这个主题和它有关系吗？
- 你最近遇到了什么现象或问题让你想学这个？

**5. 主题专属深挖问题**

根据具体主题补充针对性的问题。以下是 Android 常见主题的示例参考，实际执行时应根据主题动态生成：

- **Binder**：你知道 Binder 是做什么用的吗？你知道 AIDL 和 Binder 什么关系吗？你有没有写过跨进程通信的代码？Binder 驱动在哪一层？你知道 Binder 和 Socket 的区别吗？
- **View 绘制**：你知道 measure / layout / draw 是什么吗？你知道它们是谁触发的吗？你知道 invalidate 和 requestLayout 有什么区别吗？
- **Handler / Looper**：你知道 Handler 是干什么用的吗？你有没有在非主线程用过 Handler？你知道 MessageQueue 是怎么运作的吗？
- **Choreographer**：你知道 Vsync 是什么吗？你知道 Choreographer 和帧率的关系吗？你知道它和 View 绘制的触发有关吗？
- **Compose**：你用过 Compose 吗？你知道 Composable 的重组（recomposition）是怎么触发的吗？你知道 remember 是做什么用的吗？

**提问格式要求**：

把所有问题一次性列出，每个问题单独一行，编号呈现。不要分批问，不要先给答案，等用户统一回答后再继续。示例：

```
在开始之前，我想先了解一下你对这个主题的认知，帮我生成更贴合你需求的学习内容：

1. 你对 Binder 目前了解多少？有没有实际用过？
2. 你最想搞清楚的是什么？（可以列多条）
3. 你有没有见过但看不懂的 Binder 相关代码或报错？
4. 你是为了项目里的具体问题来学，还是想系统理解？
5. 学完后你希望能做到什么？
6. 你知道 Binder 驱动在哪一层吗？
7. 你知道 AIDL 和 Binder 什么关系吗？
8. 你知道为什么 Android 选 Binder 而不用 Socket 或共享内存吗？
9. 你有没有写过 AIDL 接口或跨进程服务？
10. ...（根据主题继续补充）

请直接回答你知道的、不确定的，不知道的就说不知道，都没关系。
```

### 收到用户回答后

根据用户的回答做以下处理：

1. **识别起点**：用户已经知道什么，不需要从零讲
2. **提炼问题列表**：把用户说出的困惑和想搞清楚的问题整理成一份"本次学习的问题清单"
3. **调整内容侧重**：用户不懂的地方多讲，已懂的快速确认或跳过
4. **在文档开头放问题清单**：作为学习主线，并在结尾逐一检验是否都回答了

## 输入要求

至少明确以下信息；如果用户未明确补充，则使用默认行为：

- 输入层级：`领域` 或 `子主题`
- 学习主题：如 `Android 图形系统`、`Binder`、`Choreographer`、`Room`
- 学习深度：默认 `deep`
- 学习目标：默认是"能讲给别人听、能实战、能画图"

如果输入的是大领域，如 `Android 开发`、`Android Framework`、`Android 性能优化`，不要直接展开多篇正文，先产出学习地图，再让用户选择子主题。
如果主题过大，先主动缩小范围，再开始输出。

## 输出策略

先判断当前输入属于哪一层：

### 领域级输入

当用户输入的是领域而不是单一主题时，先输出 1 篇 `领域学习地图.md`，不要直接展开多个子主题正文。

`领域学习地图.md` 必须包含：

- 这个领域在学什么
- 为什么值得学
- 适合什么目标的人学习
- 前置知识
- 知识树或主题树
- 推荐学习顺序
- 子主题分级与标签
- 每个子主题解决什么问题
- 哪些主题适合先学
- 下一步可选输出主题

学习地图中的每个子主题都尽量标注以下信息：

- 难度：`入门`、`进阶`、`深入`
- 优先级：`建议优先`、`按需学习`、`可后置`
- 适合目标：如"入门 Android""理解源码""优化性能"
- 前置知识：进入该主题前最好先掌握什么
- 是否可跳过：`否`、`部分可跳过`、`可跳过`
- 产出收益：学完后能解决什么问题

如果用户没有指定子主题，就停在学习地图这一层，等待用户选择下一步。

### 子主题级输入

当用户输入的是明确子主题，如 `Binder`、`View 绘制流程`、`Choreographer`，先进入问题前置环节，再根据深度输出 `主题总览.md` 或多篇学习包。

## 输出模式

以下模式仅适用于"已经明确子主题"的情况：

### `quick`

输出 1 篇 Markdown 文档，目标是帮助用户快速建立全景认知。文件名必须使用中文，默认使用 `主题总览.md`。

### `deep`

输出 3~6 篇 Markdown 文档，组成学习包。文件名必须使用中文。默认建议文件：

- `00-学习地图.md`
- `01-背景与核心概念.md`
- `02-架构与关键组件.md`
- `03-核心流程与源码走读.md`
- `04-调试性能与常见陷阱.md`
- `05-自测与延伸学习.md`

如果主题较小，可合并为更少文档，但必须保留"学习地图、自测题、下一步建议"。

## 文件命名与配图要求

- 所有学习文档统一输出到 `docs/learn/Android开发/` 目录下。
- 领域级文档默认保存为 `docs/learn/Android开发/领域学习地图.md`。
- 子主题级文档必须按主题创建子目录，保存到 `docs/learn/Android开发/[子主题名]/` 下。
- `quick` 模式默认保存为 `docs/learn/Android开发/[子主题名]/主题总览.md`。
- `deep` 模式默认保存为 `docs/learn/Android开发/[子主题名]/` 下的多篇结构化文档。
- 输出的 Markdown 文件名必须使用中文，不使用英文语义文件名。
- 文件名可以包含数字前缀以表达学习顺序，如 `00-学习地图.md`、`01-背景与核心概念.md`。
- 图示默认优先使用 Mermaid，尤其适用于架构图、流程图、时序图、分层图、对比图和时间线。
- 当 Mermaid 难以清晰表达真实结构，或存在高质量官方图示时，可以从网络抓取图片辅助讲解。
- 网络图片优先选择官方文档、标准组织、权威技术博客或教学资源中的图片。
- 使用网络图片时，必须在文档中标注来源链接、图片用途，并简要说明该图片帮助理解什么。
- 对来源不明、版权不清晰、内容失真或营销性质过强的图片，不要使用；此时退回 Mermaid 或文字说明。

## Android 专用模块

Android 主题优先补充以下内容：

- 系统分层：应用层、Framework、Native、HAL、内核
- 关键角色：真实类名、接口名、服务名、线程名
- 关键调用链：从入口到结果的主链路
- 关键代码：只选最能解释机制的源码片段或伪代码
- 调试方法：日志、trace、工具、常见观察点
- 性能与稳定性：卡顿、掉帧、内存、并发、异常场景

## Android 领域质量标准

生成内容时必须做到：

- 尽量使用真实 Android 术语和真实类名，不乱造概念。
- 涉及源码时，优先讲职责、调用关系和设计动机，不做无意义贴代码。
- 涉及系统主题时，优先说明跨进程、线程、Buffer、调度、生命周期等关键边界。
- 涉及 Jetpack 或应用框架时，优先说明抽象层、开发者感知点和常见误用。
- 如果主题与性能或稳定性相关，必须包含"如何观察问题"的内容。
