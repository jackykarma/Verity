# Feature Scenario Documentation Generator

为项目中的业务功能生成完整的场景文档，覆盖该功能**所有正常与异常场景**，每条场景以**三段式**描述：**前提（Precondition）、操作（Action）、预期结果（Expected Result）**。

产出的场景文档可直接用于：
- 产品/业务走查（逐条过）
- QA 测试用例参考
- 新人快速理解功能边界

## 与技术文档的关系

| 文档 | 面向读者 | 核心内容 |
|------|---------|---------|
| `技术实现*.md`（`feature-doc-suite`） | 工程师 | 架构、类图、时序图、接口、实现细节 |
| `场景地图.md`（本 skill） | 产品、测试、新人 | 所有用户可见的场景、操作与预期表现 |

两者配合构成完整的功能文档集。

---

## 适用场景

- 新功能上线，需要输出可走查的场景清单
- QA 需要基于场景快速覆盖测试用例
- 产品复查功能覆盖度，确保没有遗漏的边界场景
- 新人快速理解功能的完整行为边界
- **遗留功能补文档**，无任何 spec/设计文档，仅有代码

---

## 模式识别（首先执行）

在开始前，确认当前功能属于哪种模式：

| 条件 | 模式 |
|------|------|
| 存在 `spec.md` 或 `ux-design.md` 等需求/设计文档 | **有文档模式** |
| 仅有代码，无任何需求或设计文档 | **遗留代码模式** |
| 部分有文档，部分靠代码补充 | **混合模式**（以有文档模式为主，对无文档部分执行遗留代码模式信源策略） |

两种模式的**核心原则和文档格式完全相同**，差异仅在于**信源优先级**和**读码顺序**。

---

## 核心原则

### 1. 场景完整性优先

**必须覆盖所有场景**，包括：
- 正常主路径场景（Happy Path）
- 正常边界场景（边界值、最大/最小）
- 异常/错误场景（输入非法、网络失败、权限不足等）
- 中断/取消场景（用户主动中断）
- 竞态/并发场景（若功能涉及）
- 跨功能/跨页面流转场景（若适用）

**禁止只写 Happy Path**，异常场景与 Happy Path 同等重要。

### 2. 三段式格式（强制）

每条场景必须包含三个要素：

| 要素 | 说明 | 举例 |
|------|------|------|
| **前提** | 执行该场景前的系统状态、用户状态、数据状态 | "用户已登录；购物车中有 2 件商品；网络连接正常" |
| **操作** | 用户或系统执行的具体步骤（可按序号列出） | "1. 点击「去结算」按钮 2. 确认订单信息 3. 点击「提交订单」" |
| **预期结果** | 应看到的结果：界面变化、数据变化、提示信息、跳转行为等 | "显示「订单提交成功」Toast；跳转到订单详情页；购物车清空" |

### 3. 前提要写明所有必要条件

前提须明确到可操作的程度：
- 用户状态（已登录/未登录/账号已禁用）
- 数据状态（有数据/无数据/数据异常）
- 网络状态（正常/弱网/断网）
- 权限状态（已授权/未授权/已拒绝）
- 其他依赖条件（依赖的 Feature Flag、配置开关等）

### 4. 操作要具体，不要模糊

- ✅ "点击页面右上角「...」菜单，选择「删除」"
- ❌ "用户进行删除操作"

### 5. 预期结果要可验证

预期结果须描述到可被验证的程度：
- ✅ "显示错误提示「手机号格式不正确」；输入框边框变为红色；提交按钮保持禁用状态"
- ❌ "显示错误提示"

### 6. 基于事实，而非臆测

- ✅ **已确认场景**：有明确的文档依据或代码逻辑
- ⚠️ **推断场景**：基于代码逻辑推断，须标注并建议与产品确认

## 使用流程

### 步骤 1：理解范围与识别模式

确认用户指的是哪个功能，识别所有子功能边界（按页面/用例/业务流程划分）。**同时确认当前属于哪种模式**（有文档 / 遗留代码 / 混合）。

---

### 步骤 2：信源收集（按模式执行）

#### 有文档模式——信源优先级

| 优先级 | 信源 | 用途 |
|--------|------|------|
| ★★★ | `spec.md`（FR/AC） | 主干：定义"应该发生什么" |
| ★★★ | `ux-design.md`（交互规则） | 补充边界态、异常态、交互细节 |
| ★★☆ | 代码（实现） | 验证文档意图是否已实现；发现未文档化的行为 |

代码在有文档模式中的作用：发现**文档有但代码未实现**的场景（标注 ⚠️ 未实现），以及**代码有但文档未提及**的行为（标注 ⚠️ 待确认）。

#### 遗留代码模式——信源优先级

代码是唯一事实源，但读码方式决定质量。**按以下优先级收集信源，再读实现代码**：

| 优先级 | 信源 | 价值 | 读取方式 |
|--------|------|------|---------|
| ★★★ | 单测 / 集成测试（`*Test.kt`）| 前人写的"应然"规约，比实现更可信；`given/when/then` 命名直接对应场景 | 搜索 `*Test.kt`，读断言与命名 |
| ★★★ | ViewModel/Presenter 公开方法、UI 事件绑定 | 最接近用户意图的代码层 | 从 Fragment/Activity 的 `onClick`、`collect`、`observe` 入口往下追 |
| ★★☆ | 接口 / 抽象类定义 | 契约描述，噪音比实现代码少 | 读方法签名与 KDoc/Javadoc |
| ★★☆ | Git commit message（相关文件范围） | 揭示"为什么"，补充行为意图 | `git log --oneline -- <文件路径>` |
| ★★☆ | 代码注释、KDoc、TODO/FIXME | FIXME 揭示已知缺陷，TODO 揭示未完成意图，均是隐性场景 | 全局搜索 `TODO`、`FIXME`、`HACK` |
| ★☆☆ | UseCase / Domain 业务判断分支 | 补充业务规则与边界条件 | 读 `when`/`if`/`require`/`check` |
| ★☆☆ | Repository / Service 实现 | 最后读；补充网络/数据库异常路径 | 聚焦 `try-catch`、`onError`、`onFailure` |

#### 遗留代码模式——读码顺序（外→内）

**必须从外往内读，禁止从 Repository 往上读**：

```
① Fragment / Activity
   UI 事件绑定（onClick, onTextChanged 等）
   状态收集（collect, observe）
        ↓ 触发哪些 ViewModel 方法？
② ViewModel / Presenter
   公开函数与 StateFlow/LiveData 定义
   副作用（side effects）
        ↓ 调用什么 UseCase/Domain？
③ UseCase / Domain
   业务判断分支（when/if）
   前置校验（require/check）
   业务规则限制
        ↓ 才进入
④ Repository / Service
   仅关注：异常类型、错误码、重试逻辑
   不需要理解完整的数据获取细节
```

> **为什么这个顺序更好？**
> 从 Repository 往上读时，你看到的是数据操作，不是用户行为。
> 从 Fragment 往下读时，你看到的是用户可触达的每一个入口和可观察的每一个状态变化——这才是场景的本质。

---

### 步骤 3：场景提取要点

无论哪种模式，重点提取以下内容：

#### 3.1 入口与触发点
- 所有用户可触达的入口（按钮、菜单、手势、系统回调等）
- 每个入口对应的触发条件与前提状态

#### 3.2 正常流程
- 从每个入口到成功结果的完整路径
- 流程中的分支决策点（不同输入 → 不同结果）

#### 3.3 边界条件
- 校验逻辑（最大值、最小值、空值、格式校验）
- 状态机：所有可能的状态及状态转换条件
- 业务规则限制（金额上限、次数限制、时间窗口等）

#### 3.4 异常处理
- `try-catch`、`error callback`、`onFailure` 等错误处理
- 每种异常的用户可见表现（错误提示、降级展示、重试机制）
- 网络异常、权限异常、数据异常的处理逻辑

#### 3.5 跨功能流转
- 功能与其他模块的交互边界
- 页面跳转、数据传递、回调场景

#### 3.6 遗留代码专属提取点

仅遗留代码模式需额外关注：

- **测试文件中的断言**：每个 `assert*` / `verify*` 断言描述一个预期行为，直接映射为场景预期结果
- **`TODO/FIXME` 标注**：
  - `FIXME: 用户未登录时此处会崩溃` → 未登录异常场景（⚠️ 已知缺陷）
  - `TODO: 处理弱网重试` → 弱网场景（⚠️ 未实现）
- **被注释掉的代码**：可能是曾经存在但被临时关掉的功能场景
- **多余的 null 判断 / 防御性代码**：揭示真实环境中出现过的异常状态

---

### 步骤 4：组织场景结构

按子功能（或业务主题）对场景分组，每组内按以下顺序排列：
1. 正常主路径场景
2. 正常分支/边界场景
3. 异常/错误场景
4. 中断/取消场景

### 步骤 5：生成文档

按[文档模板](#文档模板)生成 **`场景地图.md`**（文件名须为中文），保存到 **`docs/project/features/[功能中文名]/`**。

## 场景编号规范

- 格式：`SC-序号`，按子功能分段，如 SC-01~SC-09 对应子功能一，SC-10~SC-19 对应子功能二
- 跨子功能场景：SC-90 起

## 实施规范

### 禁止事项

- 只写 Happy Path，遗漏异常场景
- 前提条件模糊（如仅写"用户已登录"而未说明数据状态）
- 操作步骤模糊（如"用户进行提交"）
- 预期结果不可验证（如"显示成功提示"而未说明具体提示内容）
- 遗漏中断/取消场景
- 场景与代码逻辑/文档不符（须有依据）
- **遗留代码模式**：从 Repository 层开始读码（应从 Fragment/ViewModel 入口开始）
- **遗留代码模式**：忽略测试文件，仅读实现代码

### 必须事项

- 每条场景必须包含三段式：前提、操作、预期结果
- 必须覆盖所有正常主路径场景
- 必须覆盖所有有明确处理逻辑的异常场景
- 前提须明确到可操作/可重现的程度
- 预期结果须具体到可被验证的程度
- 不确定的场景须标注 ⚠️ 并说明推断依据
- 文档说明中必须填写**文档模式**与**信源**字段
- 存储路径：**`docs/project/features/[功能中文名]/场景地图.md`**

### 完整性

- [ ] 已识别并声明文档模式（有文档/遗留代码/混合）
- [ ] 每个子功能都有对应场景分组
- [ ] 正常主路径场景已覆盖
- [ ] 边界条件场景已覆盖（空值、最大/最小值、格式限制等）
- [ ] 代码或文档中有明确处理的异常场景均已覆盖
- [ ] 中断/取消场景（如适用）已覆盖
- [ ] 跨功能流转场景（如适用）已覆盖

### 遗留代码模式专项

- [ ] 已优先读取测试文件（`*Test.kt`）作为信源
- [ ] 读码顺序为 Fragment → ViewModel → UseCase → Repository（外→内）

- [ ] 已检查接口/抽象类定义作为契约参考
- [ ] 已检查 git commit message（相关文件范围）
- [ ] 推断场景已标注 ⚠️ 推断
- [ ] 已知缺陷场景已标注 ⚠️ 已知缺陷

### 格式

- [ ] 每条场景均包含三段式（前提、操作、预期结果）
- [ ] 场景编号连续、无重复
- [ ] 文档说明中填写了文档模式与信源

### 质量

- [ ] 前提条件明确，可重现（包含用户/数据/网络/权限状态）

- [ ] 不确定场景已标注 ⚠️ 并说明推断依据和代码位置

## 示例对话

**用户**：创建购物车功能的场景文档

**助手（有文档模式）**：
1. 检测到 `spec.md` 存在，使用**有文档模式**。
2. 读取 `spec.md` 的 FR/AC 作为主干，`ux-design.md` 补充交互细节。
3. 探索购物车相关代码，交叉验证文档意图是否已实现。
4. 标注 spec 中定义但代码未实现的场景（⚠️ 未实现）。
5. 按模板生成 `场景地图.md`，文档模式：有文档模式，信源：spec.md、ux-design.md、ViewModel 代码。

---

**用户**：给遗留的用户登录功能补一份场景文档

**助手（遗留代码模式）**：
1. 未发现 `spec.md` 或设计文档，使用**遗留代码模式**。
2. 信源收集顺序：
   - 先搜索 `LoginTest.kt`、`AuthTest.kt` 等测试文件，提取断言作为场景基础
   - 从 `LoginFragment` / `LoginActivity` 的 UI 事件绑定开始读码
   - 顺序追踪：LoginFragment → LoginViewModel → LoginUseCase → AuthRepository
   - 搜索相关文件中的 `TODO/FIXME` 提取隐性场景
   - 查看相关文件的 git log，补充历史意图
3. 按外→内顺序完成场景提取，推断场景标注 ⚠️ 推断。
4. 生成 `场景地图.md`，文档模式：遗留代码模式，信源：LoginTest.kt、LoginViewModel.kt、git log。
