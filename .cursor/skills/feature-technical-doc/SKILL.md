# 功能技术文档生成器

为项目中的业务功能生成完整的技术实现文档，面向工程师，覆盖架构、类图、时序图、流程图、数据结构、接口、错误处理等全部技术细节。

## 适用场景

- 新功能上线，需要补齐技术文档供团队共享
- 新人入职，需要深入理解某个业务模块的技术实现
- 存量系统缺乏结构化技术文档
- 代码 Review / 架构演进前做系统梳理
- 与 `feature-scenario-doc` 配合使用，技术文档 + 场景文档构成完整功能文档集

## 多子功能时的文档拆分原则

- **功能目录名**：`docs/project/features/[功能中文名]/`，使用简体中文功能简称（与产品称呼一致）
- **若功能包含多个子功能**：用一篇 **功能概览.md** 整体介绍，再为每个子功能生成一篇 **技术实现-{子功能中文名}.md**（如 `技术实现-支付.md`）
- **若功能为单一功能**：直接生成一篇 **技术实现.md**，无需功能概览

```
Feature（业务功能）
 ├─ 功能概览.md              （仅多子功能时）功能整体介绍、子功能列表与关系
 ├─ 技术实现.md              （单一功能）技术实现文档
 ├─ 技术实现-子功能A.md      （多子功能）子功能 A 技术文档
 └─ 技术实现-子功能B.md      （多子功能）子功能 B 技术文档
```

## 核心原则

### 1. 基于事实，而非臆测

所有内容必须来源于：代码结构、命名、注释、配置、已提供上下文。**不得凭经验"补全业务"**。

### 2. 明确区分信息确定性

- ✅ **已确认信息**（From Code / Config）
- ⚠️ **合理推断**（Inference Based on Code，须说明推断依据）

### 3. 新人优先（New Joiner First）

默认读者：第一次接触该模块的工程师。禁止只给结论不给背景，禁止只用类名代替概念说明而不加解释。

### 4. 时序图文字说明（强制）

每张时序图代码块**紧下方**必须有「协作者与过程说明」章节，内容须覆盖：
1. **触发与入口**：谁、在什么条件下发起交互
2. **协作链与职责**：沿调用方向每一跳「谁调用谁、为了什么、输入/输出语义」
3. **工作过程与数据流**：中间状态变化（内存/缓存/持久化/网络）；关键业务决策在何处做出
4. **分支与异常**：图中每个 `alt/else` 分别说明进入条件、各分支差异行为、最终可见结果
5. **结束条件**：正常结束与各类异常结束分别是什么

**禁止**：仅一句话概括、仅列 participant 名单、或逐条机械重复图中消息而无解释。

## 使用流程

### 步骤 1：理解范围

确认用户指的是哪个模块/包/功能，判断是否包含多个子功能（按包/模块/用例边界划分）。

### 步骤 2：代码探索

按以下层次收集信息：

#### 2.1 架构全景探索

- 使用 Glob 找到相关的代码文件
- 识别所有关键类和接口，理解模块间依赖关系，确定数据流方向
- 识别外部依赖（数据库、API、第三方库，排除 project 依赖）

#### 2.2 端到端流程探索

- 追踪从用户操作到系统响应的完整路径
- 识别关键步骤和决策点
- 查找 try-catch、错误处理代码、降级策略和容错机制

#### 2.3 模块拆解探索

- 阅读核心类、接口、方法，理解职责边界
- 识别核心数据结构和状态管理，对外接口和协议定义，关键算法和策略实现

#### 2.4 业务概念提取

- 从类名、方法名提取业务术语（用于「领域概念」章节）
- 阅读注释理解业务规则，识别状态机、流程节点
- 查找配置文件、Feature Flag、常量定义

#### 2.5 错误处理与日志探索

- 查找自定义异常类、错误码枚举/常量，识别触发场景与处理方式
- 查找 Log.d/e/w、Timber、自定义日志工具的 Tag 与关键输出
- 查找埋点事件名称、触发时机、关键参数

### 步骤 3：生成文档

根据[文档模板](#文档模板)生成，每篇技术文档**必须包含全部章节**：

- **类图**：包含所有关键类与接口（含 `<<interface>>`），禁止虚构类名，含方法签名与职责说明表
- **时序图**：完整覆盖从触发点到响应的调用链，所有关键方法逐一体现，**不得用「...」代替**，每张含正常 + 异常（alt/else），**紧下方必须有「协作者与过程说明」**
- **流程图**：覆盖所有关键判断节点与分支，每张含正常 + 异常，与时序图一致

### 步骤 4：输出文件

保存到 **`docs/project/features/[功能中文名]/`** 目录；生成的 Markdown **文件名须为中文**（见上文「多子功能时的文档拆分原则」中的标准命名）。

## 实施规范

### 禁止事项

- 遗漏必含章节（文档元信息、功能介绍含范围与边界、领域概念、整体架构、关键模块设计含调用链、类图、时序图、流程图、关键数据结构、数据库设计、依赖 SDK 与配置、对外接口、错误码与异常处理、日志埋点与常见问题、附录）
- 类图遗漏关键类或接口（**必须包含所有关键类与接口，含 interface**）
- 时序图不完整：遗漏参与类/接口、关键方法调用，或用「...」代替（**必须逐一体现所有关键方法**）
- 时序图缺少「协作者与过程说明」章节（**强制必须**）
- 流程图不完整：遗漏关键判断节点或分支，或用「...」代替
- 时序图或流程图缺少异常分支（**每张图必须用 alt/else 覆盖正常 + 异常路径**）
- 流程图与时序图的流程节点/分支相互矛盾
- 类图、时序图使用虚构/伪造类名（须严格基于项目真实代码）
- 将 `implementation project(':xxx')` 列为依赖 SDK
- 只写 Happy Path，忽略异常、降级、错误处理流程

### 必须事项

- 存储目录固定为 **`docs/project/features/[功能中文名]/`**
- 多子功能时：生成 **功能概览.md** + 每子功能一篇 **技术实现-{子功能中文名}.md**
- 单一功能时：生成 **技术实现.md**
- 每篇技术文档**必须**包含全部章节
- 类图：包含**所有**关键类与接口（含 interface），基于真实代码，含方法签名与职责说明表
- 时序图：**完整覆盖调用链**，所有关键方法逐一体现；**每张图紧下方必须有「协作者与过程说明」**
- 流程图：**覆盖所有关键判断节点与分支**，与对应时序图保持一致
- 所有业务规则必须有代码依据；不确定的内容必须标注 ⚠️ 并说明推断依据

- [ ] 文档存放在 **`docs/project/features/[功能中文名]/`** 下

- [ ] **6. 时序图**：多张，每张**完整覆盖调用链**（无「...」省略），每张含正常 + 异常（alt/else）；**每张图紧下方有「协作者与过程说明」，覆盖触发入口、协作链、数据流、分支说明、结束条件**
