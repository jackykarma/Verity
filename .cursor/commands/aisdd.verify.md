## 用户输入

```text
$ARGUMENTS
```

在继续操作前，你**必须**参考用户输入（若不为空）。可用于：**验证范围**（全量 / 指定 Story 如 `ST-001,ST-002` / 指定阶段如 `阶段 3`）。

## 目标

在 `/aisdd.implement` 执行完毕（全部或部分阶段）后，**独立验证**代码实现是否与设计方案一致。这是一个**独立于实现者的验证视角**，避免实现过程中的"自我确认偏差"。

**与 implement 步骤 9 的区别**：
- implement 步骤 9 是实现者自验（同一 AI 上下文）
- verify 是独立验证（新的上下文，重新读取设计文档与代码，逐项对照）

## 操作约束

- **设计文档只读**：不修改 spec/plan/epic-design/story_detail_design 的内容
- **可标记 tasks.md**：在 tasks.md 中对已验证的 Task 追加验证结论标注
- **发现偏离时**：输出偏离报告，建议提交 CR 或回退实现，**不自动修改代码**

## 执行步骤

### 1. 环境搭建

从代码库根目录运行：

```powershell
.specify/scripts/powershell/check-prerequisites.ps1 -Json -RequireTasks -IncludeTasks
```

解析 `FEATURE_DIR`、`AVAILABLE_DOCS`。所有路径必须为绝对路径。

### 2. 加载设计基线（验证依据）

以下文档构成**验证基线**——实现必须与之一致：

- **spec.md**：FR/NFR/AC（功能正确性与非功能指标的判定依据）
- **plan.md**：技术规约与实现约束（架构约束、数据模型、接口契约、线程模型、错误处理）
- **epic-design.md**：0/1 层架构、全景类图/时序、Story 拆解
- **story_detail_design.md**：各 Story 的 L2 详细设计（类图、时序图、触发条件）
- **epic-plan.md**（若存在）：EPIC 级技术约束
- **tasks.md**：Task 清单与设计引用

### 3. 确定验证范围

- **全量验证**（默认）：验证 tasks.md 中所有标记 `[x]` 的 Task
- **指定 Story**：仅验证 `$ARGUMENTS` 中指定的 ST-xxx 相关 Task
- **指定阶段**：仅验证 `$ARGUMENTS` 中指定阶段的 Task

### 4. 逐 Story 验证

对每个在验证范围内的 Story（ST-xxx），执行以下验证：

#### 4.1 架构一致性验证

- 代码的模块/包结构是否与 epic-design.md §2（1 层架构）一致
- 类的分层是否符合 plan.md §3（架构约束）的依赖方向
- 新增类是否出现在全景类图（epic-design.md §4）或 story_detail_design.md 的类图中
- 是否存在类图中定义但未实现的类/接口
- 是否存在代码中新增但设计中未定义的类（允许辅助类，但核心类必须有设计对应）

#### 4.2 接口契约验证

- 实际代码中的公共方法签名是否与 plan.md §5 / story_detail_design.md 的接口定义一致
- 方法参数类型、返回类型是否匹配
- 错误处理方式是否符合 plan.md §3 的错误处理规范
- 数据模型（Entity/DTO）是否与 plan.md §4 一致

#### 4.3 行为一致性验证

- 代码的核心执行流程是否与 story_detail_design.md 的时序图一致
- 正常流程的调用链是否匹配
- 异常分支（alt/else）是否实现
- 触发条件与系统响应是否与 story_detail_design.md 的表格一致

#### 4.4 FR/NFR 覆盖验证

- 对照 spec.md 的 FR 列表，检查每个 FR 是否有对应的代码实现
- 对照 spec.md 的 AC（验收标准），检查是否可满足
- NFR 约束是否在代码中有体现（如性能相关的缓存、异步处理；内存相关的资源释放等）
- 是否存在 FR/NFR 未被任何代码覆盖的情况

#### 4.5 技术规约遵从验证

- 线程/并发模型是否符合 plan.md §3（如 IO 是否在 Dispatchers.IO）
- 日志/可观测性是否符合 epic-plan.md §9（如有）
- 命名规范是否与 plan.md §8 源代码结构约定一致

### 5. 生成验证报告

输出 Markdown 报告：

```markdown
## 实现验证报告

**Feature**：FEAT-xxx - [名称]
**验证日期**：YYYY-MM-DD
**验证范围**：全量 / ST-001, ST-002 / 阶段 3
**Task 总数**：X（已验证 Y / 跳过 Z）

### 验证摘要

| 验证维度 | 通过 | 偏离 | 未验证 | 通过率 |
|----------|------|------|--------|--------|
| 架构一致性 | X | Y | Z | % |
| 接口契约 | X | Y | Z | % |
| 行为一致性 | X | Y | Z | % |
| FR/NFR 覆盖 | X | Y | Z | % |
| 技术规约遵从 | X | Y | Z | % |
| **合计** | X | Y | Z | **%** |

### 偏离清单（按严重程度排序）

| ID | Story | 验证维度 | 严重程度 | 设计期望 | 实际实现 | 偏离说明 | 建议操作 |
|----|-------|----------|----------|----------|----------|----------|----------|
| V001 | ST-001 | 接口契约 | 阻塞 | plan.md:§5 定义... | 实际代码... | ... | 修改代码 / 提交 CR |

### Story 级验证详情

#### ST-001：[标题]

- **架构**：✅/❌ [说明]
- **接口**：✅/❌ [说明]
- **行为**：✅/❌ [说明]
- **FR/NFR**：✅/❌ [说明]
- **技术规约**：✅/❌ [说明]
- **整体结论**：通过 / 有偏离待修复

### FR/NFR 覆盖矩阵

| FR/NFR ID | 设计覆盖 Story | 代码实现状态 | 验证结论 |
|-----------|---------------|-------------|----------|
| FR-001 | ST-001 | 已实现 | ✅ |
| NFR-PERF-001 | ST-003 | 未验证 | ⚠️ 需性能测试 |
```

### 6. 偏离分类与建议

对每个偏离项分类：

- **代码偏离（应修复代码）**：实现未遵循设计，设计是正确的
  - 建议：修改代码以匹配设计
- **设计缺口（应补充设计）**：实现中发现设计遗漏，实现是合理的
  - 建议：提交 CR，补充 story_detail_design.md 或 plan.md
- **设计与实现均需调整**：发现双方都有问题
  - 建议：提交 CR，同时更新设计与代码
- **可接受偏差**：实现在细节上与设计不同，但不影响功能正确性
  - 建议：记录为已知偏差，无需修改

### 7. 标记 tasks.md 验证结果

对 tasks.md 中已验证的 Task，在其验证子项中追加结论：

```markdown
- **验证**：
  - [x] 架构一致性：通过
  - [x] 接口契约：通过
  - [ ] 行为一致性：偏离（V001）
```

### 8. 完成报告

输出：
- 整体通过率
- 阻塞性偏离数量
- 建议下一步：
  - 若无阻塞性偏离 → `/aisdd.gate implement-done`
  - 若有阻塞性偏离 → 修复后重新运行 `/aisdd.verify`
  - 若有设计缺口 → 使用 CR 模板提交变更，更新设计后重新验证

## 验证原则

- **设计为准**：除非发现设计明显有误，否则以设计文档为判定基准
- **不越权**：verify 不修改设计文档，只报告偏离
- **可重复**：相同输入应产出一致结论
- **分层验证**：架构 → 接口 → 行为 → FR/NFR → 技术规约，由粗到细
- **实事求是**：对无法验证的项（如运行时性能）标记为「需运行时验证」，不做推测

## 与现有命令的关系

- **`/aisdd.implement`**：执行实现——verify 在 implement 完成后运行
- **`/aisdd.analyze`**：分析 spec↔plan↔tasks 文档一致性——verify 分析代码↔设计一致性
- **`/aisdd.gate implement-done`**：verify 通过后可运行 implement-done 关卡
- 建议流程：implement → verify（可按 Story 分批） → gate implement-done
